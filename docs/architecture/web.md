# Web UI

Covers `web/`: routes, auth, peers, the Setup Wizard. The rules that apply everywhere are in [CLAUDE.md](../../CLAUDE.md).

## UI copy: explanations live in the help drawer (REQUIRED)

**Do not add inline help to web forms.** A `<label>` (plus a `placeholder` where
one genuinely helps) is the whole of a control's inline copy. Everything else –
what the setting does, when to use it, defaults, side-effects, caveats, examples,
and "manage X under Y" pointers – goes in that section's **help drawer markdown**
(`openfollow/web/help/<section>.md`, surfaced by the per-section `?` drawer via
`data-help="<section>"`).

- **A new `field-note` is a review blocker**, including a terse one-line pointer.
  "For a camera looking from upstage", "Comma-separated; e.g. …", and
  "Manage destinations under OSC Destinations." have all been stripped on sight.
  If the label alone doesn't identify the control, fix the label.
- When you add or change a control, update the matching
  `openfollow/web/help/<section>.md`. The help drawer is the single home
  for the explanation, so it can't drift between the form and the docs.
- The same goes for `title` tooltips carrying explanation. A `title` is fine for
  a badge or icon with no visible label (e.g. the "This session" interface badge).
- Existing `field-note`s predate this rule – leave them where they are unless you
  are already editing that block, then move the text into the help `.md`.
- `section-note` (the one-line subtitle beside a section's `<h2>`) is a *name*,
  not help: "Marker speed limits, default speed, and default position" is fine;
  a sentence teaching behaviour is not.

## Touch remote routes (`_register_touch_remote_routes`)
`/api/remote/open`, `close`, `hold`, `drive`, `action` (POST, JSON) and `state` (GET) back the card in `partials/touch_remote_card.tpl` and `static/js/touch-remote.js`, which base.tpl includes only while `touch_remote.enabled` and the `touch_remote` feature are both on. Every route answers 403 while either is off; 400 for a malformed body or a wrong-type field (a bool is never a number); 404 for an ended session (the card opens a new one and takes no marker until a chip tap); 409 for a marker this station does not control or another remote took. `drive` is the heartbeat, sent every 50 ms with one request in flight. Glide targets are not clamped to the stage, only refused beyond 10 km (`MAX_REACH_M`) as a typing slip. See [input](input.md#touch-remote-inputtouch_remotepy-inputmanagerupdate_touch_remote).

## Feature gating (`data-feature`)
The Features list (`ui.shown_features`, see [config](config.md#sub-config-notes)) hides what an off feature owns. An element that belongs to feature `<key>` carries `data-feature="<key>"`; `base.tpl` gives `<body>` one `feature-<key>` class per feature that is on and emits one `display: none` rule per key from `FEATURE_KEYS`, so a new key needs no CSS. The Features table (`partials/general.tpl`, inside Station Settings › Advanced Settings) lists `OFFERED_FEATURES`, so a config-only feature has no row, and saves with the Station Settings Save: its boxes join `#general-network-section` through `form=`, with a `features_submitted` marker so `/section/general` knows the list was on the page. `static/js/feature-save.js` asks in the shared modal before a Save switches a feature off and flips the body classes once the save succeeds, so nothing reloads, except when the touch remote's launcher appears or goes (`HX-Refresh`). The `features` section is never broadcast (`_BROADCAST_EXCLUDED_SECTIONS`). `initTabs` falls back to the first tab when the stored one belongs to an off feature. Hiding is never the gate: a route or service asks `feature_on` / `feature_gated` itself. With `lens_distortion` off the wizard drops its Lens step from `_steps`, starts from a pinhole lens and leaves the lens out of Apply, so the saved one stays; `psn_input` hides nothing.

## HTMX notes
- HTMX version: 1.9 – use `hx-on::after-request` (double colon), NOT `hx-on:htmx:after-request`
- Overview auto-refresh: every 5s while its section is in view (see the polling rule below)
- Every restart runs one flow in `base.tpl`: `openfollowRestartProgress(note?)` opens a locked progress view (`.modal-progress`, like the updater's), and `openfollowAwaitRestart(before, step?)` polls `/api/info` every 2 s and reloads the page once it answers with an `instance` other than `before`. That id (`ConfigWebServer.instance_id`, random per process) is what tells the new process from the old one, which keeps answering for the several seconds it takes to shut down; reloading on its answer lands on a station that is about to stop listening. Unreachable, 401, 403 and 503 all read as not back yet. The auth cookie is signed with the PIN, not per process, so the new process accepts the logged-in browser's cookie. A station that has not answered after 90 s gets a dismissable dialog saying so, with one next step. Every request that restarts names the process it restarts: `POST /api/restart` and `POST /api/config/reset` in their JSON (`instance`), a switch to Simple network mode that restarts in an `X-OpenFollow-Restarting` header. The Restart buttons (Diagnostics, Keyboard Input, Interface Assignment, the Simple card) run `openfollowRestart({title, message, note?, step?})`: the confirm, the progress view, `POST /api/restart` (409 while an update is queued or running, as is `POST /api/config/reset`, before it changes any setting). Restore Defaults keeps its own confirm and shows the progress view from the moment it sends. The mode switch shows it only once the answer names the process restarting: removing a VLAN may ask for the password while the request runs, and the locked view would leave the prompt unanswerable. A switch whose restart an update refused reloads with a caution toast saying so (`X-OpenFollow-Restart-Refused`). A refused or unanswered request closes the progress view (the mode switch hides its busy line) and reports through `saveError` with the action's own lead ("Not restarted.", "Not restored.", "Not switched."). A section save never restarts.

## Polling costs the station (`web/config_cache.py`)
Every request the web server answers runs on a thread of its own and reads the config first, in `_check_auth`. So an open page is never free, and anything it polls is paid for on the station, which also runs the frame loop.
- **A poll runs only while someone is looking** (`static/js/poll-gate.js`). Every `every` clause in a template carries a `[...]` condition and the trigger also listens for `poll-shown from:body`; `tests/test_web_poll_gating.py` enforces both.
  - A section poll gates on `pollShown(this)`: false while the browser tab is hidden, the section is folded, or the section is not laid out (another tab, a hidden wizard step). It measures the enclosing `.section`, so a `hidden` driver element works. `hx-trigger="every 5s [pollShown(this)], poll-shown[pollShown(this)] from:body"`.
  - A poll that lasts only while something the operator started runs (a Learn capture, the detection install, the gamepad button wizard, a Detect button, the Save to USB storage device dialog) and the page-wide privilege prompt gate on `[!document.hidden]` only, so folding a section does not stall them.
  - `announcePollsShown()` fires `poll-shown` when the browser tab is shown again, on a tab click or cross-tab link, and on an unfold, so a poll coming into view refreshes at once instead of on its next tick. Page load does not fire it.
  - A live readout polls only after the operator asks, for a bounded time: the MIDI fader strips use **Show live**, every 500 ms for 10 s (`midiLiveActive() && pollShown(this)`).
  - A script-driven poll does the same: the Video Source snapshot preview and the Zone Editor check `pollShown` before each fetch and refresh on `poll-shown`; the Ground Grid and Path Editor fetch only while their own canvas or list is laid out in a visible tab; the pushed-settings check skips while the tab is hidden and asks again on `visibilitychange`.
  - Two script polls are not gated: the restart progress view's `/api/info` and the updater's progress. Each holds a locked view until the station answers, and its give-up is timed from when it began, so a tab hidden past it would come back to a give-up the station was never asked about. Both are bounded (90 s, 15 min) and run while the station restarts or installs.
- **Each request's config is parsed once per change.** `ParsedConfigCache` keys the parse on the file's device, inode, mtime and size, and keeps only a strict, successful parse of a file that still has that key afterwards: a read that failed, or a file that changed or went away while it was read, is served through `load_config`'s fallback and never kept, because the defaults it falls back to carry an empty `web_pin`. A kept parse is reused only while the key holds and two more things are true: its read began at least a second away from the file's mtime, either way (an edit in place of the same size within one mtime tick would not move the key; a clock set behind the mtime, as on a Pi with no RTC after a power cut, still caches), and `[otp_output]` has no non-blank `source_ip` without a `source_iface` (`load_config` resolves that address against the live interfaces on each read). A parse not reused is still the last whole read a broken file is served as. Each request gets its own copy, unpickled from the stored bytes, so a handler that changes its config in place reaches no other request. Saves still load a fresh config under the write lock.

## Setup Wizard (`/wizard`)
Four steps; the camera is solved from marks the operator pins on the snapshot, each with a known or measured position, so the origin comes from the measurements:
1. **Video Source** – select and configure the camera input (reuses the video source UI); **Save** or **Save & Next**. Carries the Video Source panel's failure box, polled only while it shows (`[pollShown(this)]`)
2. **Lens** – measure `lens_k1` / `lens_k2` from lines that are straight in reality, about the lens centre `lens_cx` / `lens_cy`, which is typed under User input or loaded, never measured (see "Lens distortion from straight lines" below), or load a saved lens; skipping keeps the current lens. Only with `lens_distortion` on. `ui.developer_mode` (config-only, no form control) adds a **Show edges** checkbox that lays the edge map the suggestions were picked from over the snapshot
3. **Camera Calibration** – two modes on one solve (see "Camera calibration from marks" below). **Simple**: four numbered questions that open in order (`lockSimpleSteps`: a step is `step-locked` and `inert` until the one before it is done; a rectangle already entered counts as the first done): the camera's location with an optional camera position checked against the solve, the rectangle's width and depth (empty, no placeholder), the point of origin (an active choice from "Choose…": Default, centred between DSL and DSR, or Custom, the rectangle's centre from the origin; a station whose saved grid gives one keeps it), then the four corners (DSL, DSR, USR, USL) on the picture. Refresh Image is locked with the fourth step, **Reset Corners** shows once a corner has moved, and **Next** stays off until all four are placed. **Advanced**: the camera position first, then known points and distance points (kind `triangulated`) placed through a menu on the picture. **Switch units** posts `/settings/unit-system` and converts every length already entered
4. **Review** – the grid through the solved camera, every placed mark and 0/0/0; the caution, camera, lens, calibration and grid values; **Save and finish** (disabled without a solve) or **Leave without saving**

Key implementation details:
- **Steps are keyed, never numbered, in script.** The template builds the step list (`_steps`: `video`, `lens`, `calib`, `review`) and publishes it as `window.WIZ` (key → index) and `WIZ_STEPS`; step content divs are `#wizard-step-<key>`, nav buttons call `wizardNext()` / `wizardPrev()`, and the session stores `stepKey`. A step inserted or left out shifts nothing
- **The help drawer per step.** Each section head's **?** carries `data-help-open="wizard-<step>"` (`help/wizard-video.md`, `wizard-lens.md`, `wizard-review.md`); Camera Calibration's carries `wizard-calibration-simple` or `wizard-calibration-advanced`, and a drawer open on it follows a mode switch
- **The station solves; the page draws.** Every pin change posts the marks to `/api/wizard/solve` (`solveSoon`, 40 ms debounce); `solveSeq` drops the answer to an older solve, and the body names its page (`WIZ_SOLVE_PAGE`) so the station stops a superseded fit. The page checks only what a solve needs first (`solveState`: Simple waits for a readable rectangle and all four corners moved, Advanced names the camera position, known and pinned points missing, as the route's 422 does). It projects for drawing only (`wizProject`, mirroring `scene/solver.project_points`, then the lens bow): the starting rectangle, the grid through the solved camera, 0/0/0 (through the corners' homography before the solve), the Distances to check lines, and a distance point's pre-solve X / Y / Z (`wizTrilaterate`, the mirror side picked by the pin's side of the line between its two points' pins)
- **Simple's starting rectangle** (`startQuad`, `wizFitQuad`): the rectangle as a camera at the entered position, else the chosen location (`CAM_PRESETS`), else 15 m in front of it and 8 m up, looking at its centre with the saved FOV sees it; scaled to at most half the picture's width and height (one under 20 % in both scaled up to that), kept 5 % inside the frame, bowed by the lens. A corner not yet moved (`cornerMoved`) follows every input; the solve waits for all four
- **Advanced's picture menu**: a click opens **Which point is here?** at the spot (the unpinned points, **New known point**, **New distance point**, disabled until two known points read or at `MAX_CALIBRATION_MARKS`); a pin's click opens **Remove pin** / **Delete point**. While it is open the loupe stays on the spot and the arrow keys move it unless a field has the focus. Deleting a point removes it from every Measured from that named it
- **Mode switch**: Simple → Advanced turns the corners into known points with their pins and keeps the camera position; Advanced → Simple with points asks first (the shared modal, only the confirm red), then clears them
- **Full screen** (`openFull` / `closeFull`): the picture's container moves into `#fs-shell` and back; the shell asks for browser full screen and fills the window where that is refused. The picture keeps its aspect (`fsLayout`); one toolbar (`renderFsBar`: title, hint, status, the Lens step's **Point off** / **Delete line**, **?**, **Exit full screen**) and a non-modal key panel (`fsHelpHtml`, toggled by **?** unless a field has the focus). Esc, or the browser's own exit (`fullscreenchange`), ends full screen and cancels whatever is active; on the page Esc ends one thing at a time: an open menu, a selection, a started line
- **Pins are snapshot pixels in the page and fractions everywhere else.** The config (`CalibrationMarkConfig.pin`) and the session keep fractions of the snapshot; `pinsToSnapshot` maps them once the snapshot's size is known and moves pixel pins with a snapshot of another resolution. The solve route takes pixels plus the canvas size; Save and finish posts fractions
- **Session**: `sessionStorage['openfollow:wizard']` keeps the step key, the lens lines, fit and rejected suggestions, the pair and the lens centre, the mode, location, rectangle, corner pins, points, camera position, camera height, unit system and the lens state, and is restored only in the shape the page draws (a session from another version never stops the page from opening). A session typed in other units keeps the lens and starts the calibration afresh. Without one, `loadSaved` starts from the station's calibration (`WIZ_SAVED`): its mode, Simple's rectangle and origin from the grid, the marks with their pins, the camera height. The camera position always starts empty
- **The script's maths is tested by running it.** `tests/test_wizard_js.py` pulls named functions out of `wizard.tpl` (`tests/_wizard_js.py`, by brace matching) and runs them in node against the Python they mirror: the projection and look-at against the solver's, trilateration and its side rule, the origin through the homography, the starting rectangle, the lens warp both ways, its limit radius and validity with and without a lens centre, the centre's pixels, the band and edge-map geometry, the loupe's spot, the suggestion bubbles' placement and outline, a settings file's lens, the caution wording from `plausibility()` and the imperial length read. It skips where node is not installed. A function it calls must stay pure: pass in what it reads from the page
- SVG viewBox matches native image resolution so coordinates map 1:1 regardless of CSS scaling
- Touch-friendly: `touch-action: none` on the pictures. The viewBox is the snapshot's resolution, so handles, labels and strokes are sized in CSS pixels (`overlayPx`, `vector-effect: non-scaling-stroke`) and drawn again on a resize
- An imperial length field's text maps back to the metres it was written from (`exactLen`), since ft / in text rounded to 0.01 in reads back with a residue (0.5 m as 0.500126 m, a grid line more)
- The Lens step works from the keyboard: each suggestion's bubble holds two buttons (**Use this line**, **Reject this line**) and a choice moves the focus on to the next bubble, every point has an `aria-label`, a focused point is the selected one, with a point held Tab / Shift+Tab step through its own line's points and leave the line past its last or first point (never a focus trap; the browser moves on in page order), Enter / Esc end the hold with the focus kept on the point (the same for a Simple corner, so the next Tab moves on), no SVG element carries a focus listener (Chrome would make it an invisible Tab stop; the listeners sit on the HTML containers), and Delete leaves the focus on the next line or the picture
- **Save and finish** (`applyAndFinish`) uses the JSON API to avoid resetting unrelated bool fields: in Simple `POST /api/config/grid` with the rectangle first, then `POST /api/config/camera` with the pose, `calibration_mode`, `calibration_marks` (pins as fractions, a distance point's solved `position`), `calibration_height` (null when not entered) and the lens, `lens_k1`, `lens_k2`, `lens_cx`, `lens_cy` (only with `lens_distortion` on). The grid goes first because Simple's corners follow the grid and a corner the grid moved loses its pin. Each response's `.ok` is checked before the session is cleared and the page leaves (silent-drop regression guard in `tests/test_wizard.py`)
- **Input validation:** `/api/wizard/solve`, the `/api/wizard/lens/*` routes and the lens calibration save must return 400 – not 500 – on malformed bodies. All float coercion and shape checks (including numpy array construction from caller-supplied coords) belong *inside* the try/except, which catches `OverflowError` too: JSON carries an integer of hundreds of digits exactly, and `float()` of it raises. Numbers are read strictly (`_json_number` / `_json_int` / `_json_point`), and `_require_wizard_canvas` refuses a canvas side outside `(0, 16384]` (a canvas of 1e170 overflowed the Lens snap into a solve that never returned)
- **Step nav semantics:** `<nav aria-label="Setup Wizard steps">` landmark with `aria-current="step"`, **not** `role=tablist`/`role=tab`. A tablist without `aria-selected` / `aria-controls` / `role=tabpanel` is an incomplete ARIA tab pattern; for a linear wizard, nav + aria-current is the correct lighter-weight semantics
- Snapshot blob URLs: `loadSnapshot()` must revoke the previous `URL.createObjectURL` after the new image loads to avoid a per-refresh memory leak
- "No feed" UX: each preview container has a sibling `.wizard-no-feed` placeholder div; `setPreviewVisibility()` toggles both so the snapshot steps never render blank when `/api/video/snapshot/full` fails

## Lens distortion from straight lines (`scene/lens_fit.py`, `scene/edge_snap.py`, `scene/edge_chains.py`, `lens_model.py`)

**The operator never reads `k1` or `k2`.** Every label, result line, hint and help paragraph, in the Setup Wizard and on the Camera form, calls the pair **Barrel / fisheye** (`lens_k1`) and **Corner correction** (`lens_k2`), and `lens_cx` / `lens_cy` the **Lens centre** in whole pixels; the field names, the API keys and the code keep the coefficient names.

The overlay follows the lens with the two-term **division model** about a **lens centre** (`lens_model.py`'s docstring is the one definition): a screen point `v` half-diagonals from the lens centre `c = (lens_cx, lens_cy)` (image axes, y down) is at pinhole radius `r_u = r_d / (1 + k1·s + k2·s²)`, `s = r_d²`, and the lens centre is the pinhole principal point. Barrel is negative, the slope at the lens centre is 1, so `fov` keeps its paraxial meaning, and radii over the half-diagonal make a lens fit any resolution of the same picture shape. `project_points` / `unproject_to_plane` stay pinhole, `apply_overlay_distortion` bows what the HUD draws (pinhole to screen: closed form for `k2 = 0`, else a per-pair table seed polished by Newton, with a bracketed solve for anything left) and `invert_overlay_distortion` undistorts clicks, detection pins and zone feet in closed form; both take `cx, cy` with no default. **The one validity rule** is `lens_model.lens_warp_is_valid` (stdlib-only, because `configuration.py` reads it): the map must be defined and rising out to the frame corner farthest from the lens centre, at most `1 + |c|` half-diagonals away, so neither `1 + k1·s + k2·s²` (the pole) nor `1 - k1·s - 3·k2·s²` (the fold) reaches 0 for `s` up to `(1 + |c|)²`; `lens_limit_radius` is the closed form, each axis of the centre is bounded by `C_BOUND` (0.25, 275 px at 1080p) and a value past 1e3 is refused outright, where `k1²` would overflow. Under barrel every pinhole point has a screen point inside the pole, so a grid line to the horizon bends onto a disc instead of folding back; past a pincushion fold a pinhole radius lands on the fold radius, and a screen point at or past the limit has no pinhole point (NaN). `CameraConfig.__post_init__` clamps the centre into its bound and pulls a lens that cannot reach the corners back along the pair's own ray (`pull_back_to_valid`: closed form, `PULL_BACK_MARGIN` short of the limit, the centre never moved) with one WARNING naming both lenses, and only a value that is no number reads as 0. The Camera form checks the lens through `validate(..., context=)` whenever any value, slider or centre field changes (each lens input's `hx-trigger` adds `change from:` the others, since a slider writes its field without a blur), reading an empty sibling as its saved value as the save does (`needs_cfg`), and names the pair while it alone falls short, else the centre. Its centre fields count whole pixels of the live video (`_camera_video_size`, from the runtime stats) and write the hidden `lens_cx` / `lens_cy` in half-diagonals, as the sensor helpers write `fov`; a field without a number in its pixel bound says so itself and is not sent, and without video both are off ("No video") and the hidden fields keep the saved centre. `_wizard_lens_coeffs` pulls back the same way, and the fit never leaves the valid region. `wizard.tpl` mirrors the rule and both directions (`wizLensLimitRadius`, `wizLensIsValid`, `wizApplyDistortion`, `wizInvertDistortion`) for its bowed edges, live curves and the settings file.

**The fit** (`fit_lens_from_lines`) is the plumb-line method: each traced line's active points are undistorted and measured against their own total-least-squares line, its direction taken from the line's first point toward its last (the SVD's sign is free, and one that flips between the Jacobian's two samples flips every residual). Each residual is divided by the undistortion's closed-form Jacobian along the line's normal, so it is in **screen pixels**, where the placement noise lives, and the line itself is refitted with the same weights. **The fit never measures the lens centre**: it holds the one the request names (`cx`, `cy`, typed or loaded in the wizard) fixed. A coarse grid over the pair (vectorised through `_Lines.grid_cost`, cells past the limit dropped) seeds a Levenberg-Marquardt refinement of `k1`, `k2` about that centre, because a start at zero diverges on strong barrel distortion. **A gentle prior draws the pair toward no lens** (`K1_PRIOR` 0.25, `K2_PRIOR` 0.2, the sigma of each coefficient), weighed against the points' own scatter (floored at `_PRIOR_FLOOR_PX`), so it decides only along a ridge the lines leave open. The pair it draws is always the answer: `k2` is never dropped to 0, which trades the corners' bend into `k1` and bends the middle of the picture wrong. `k2_fitted` says whether the lines (their own sigma of `k2` below `K2_PRIOR`) or mostly the prior set `k2`; the page applies an estimated `k2` as well and marks it "(estimated)". With lines placed to a fraction of a pixel the estimate is mostly theirs and can be large. **Strays**: before the lens is fitted, a point that misses the line through its line's other points by more than `_STRAY_SIGMAS` sigmas of that miss (a robust scatter floored at 1 px, inflated by how far the others' line is extrapolated) is set aside, at most one a line of at least `_STRAY_MIN_POINTS`, and only while those other points lie on a line under the lens the other lines agree on (refitted without the line; an F test at `_STRAY_STRAIGHT_TAIL` against the others' scatter plus the refit's own uncertainty at those points): a line that bends throughout keeps its points and is flagged instead. Judged under the lens it pulled its way, a bowed line's other points run straight, an end of it is set aside and a straight line elsewhere takes the blame. `dropped` names the point. The rating is the predicted uncertainty in px of where the **pinhole frame's corners** land on screen, from the posterior covariance of the pair (the prior included), the residual sigma floored at 1 px, a corner landing outside the picture taken where the picture ends; or, when larger, how far apart the fit and another minimum the seeds reached put the screen points, if that minimum's cost is within `_RIVAL_MARGIN` residual variances of the best. The covariance sees only its own minimum: traced along the top and bottom edges alone, a strong barrel lens and one about 0.15 weaker fit the points equally well, some 25 px apart, and either rated excellent. **Lines that never reach out** measure the middle of the picture only: unless points reach beyond `_REACH_RADIUS` (0.8 half-diagonals) of the lens centre on two different of its four sides (right, up, left, down; one line may reach both; `_reaches_out`), the answer carries `edges_measured` false. The rating keeps its value for the middle. The page shows a Good or Excellent fit with `edges_measured` false as Fair, "but might already be good in the middle", with a sub-line in place of the hints and a hint box asking for lines near the edges; the lens it saves is the same. Fair and lower keep their own result and hints. `RATING_THRESHOLDS_PX` (2.5 / 5 / 10 / 20 → excellent / good / okay / medium, else low; the page names them Excellent, Good, Fair, Poor, Not usable) are fixed from simulation (`scripts/lens_fit_simulation.py`) and pinned in `tests/test_lens_fit.py`. The hint (`coverage_hint`) asks for a second line, then for a line into a corner while the corner correction is unmeasured and no line reaches one, then names every edge whose outer 15 % holds fewer than 5 points, weakest first, always "If possible", since a picture may show nothing straight there: "If possible, add …" below Good, "If possible, add … to confirm it." at Good or better, and "The result may already be good. If possible, add … to confirm it." when the lines already agree (at least 4, none misfit, 1.5 px RMS or less, the corner correction measured, Fair). A line **does not fit the others** when, with the pair refitted without it (the prior keeping two remaining lines from being overfitted; a line alone in its part of the picture, such as another system's on-screen graphic, sets `k2` there, and only a refit of both coefficients sees it bent), its RMS exceeds the floor `_MISFIT_MIN_PX` (2 px), `_MISFIT_RATIO` times the displacement the refit's own uncertainty predicts at that line, and what placement noise gives a straight line once in `1 / _MISFIT_TAIL`: an F test of its scatter on its own degrees of freedom (its points less two) against the others' (the floor sits a little above what the test asks of a scatter at the 1 px placement floor). One line is set aside at a time and the rest refitted and judged again: of the lines that do not fit, the one that misses most among those without which the others agree about as well as without any (left out, a line a bent one leans on can miss more than the bent one, but the others then scatter). Needs three lines. Curved edges that bend alike on both sides of the picture (the two edges of a pair of drapes) agree with a lens of their own and pass. A pinhole lens reproduces the pinhole path exactly.

**Edge snap** (`snap_line_to_edges`) runs on a luma band the browser cuts along the traced chord (`lensBand()`: one canvas `drawImage` with a rotating transform, so the server never needs the JPEG decoded and the snapshot the operator sees is the one measured): one column per `band_step` pixels of the chord, one row per pixel across it, `band_half_size` rows to either side, both mirrored by the wizard and pinned by a test. A straight edge seen through a lens is a smooth curve: its offset from the chord is a shift of either end plus the bows of the two lens terms (drawn about the frame centre with `_REFERENCE_K1` / `_REFERENCE_K2`; the end shifts absorb a lens centre's effect on a short chord). So the snap only ever follows such a curve, never a path that may step from one edge to its neighbour. **A hand-traced line** is anchored where it was clicked: each end takes an edge peak within `end_search_radius` of the click (16 px at 1080p; the `_END_CANDIDATES` nearest per end and polarity, or `_FREE_END_OFFSETS` offsets across the reach where it has none), and every curve through two such ends, bowed no further than the strongest plausible lenses (`_PLAUSIBLE_LENSES`, a 150° fisheye and a pincushion) bow that chord times `_BOW_MARGIN` plus `_BOW_SLACK`, is scored by the share of its columns with an edge peak on it: a straight edge runs on along the curve, clutter only crosses it, and strength only breaks a tie. Of the curves scoring at least `_CREDIBLE` of the best, the one anchored nearest the clicks wins, so of two parallel edges the click says which is meant. **A used suggestion** (`NearEdge`: its five samples and the polarity the edges route found) already lies on its edge: the curve starts through its samples, and each point is looked for only within `point_window` (4 px at 1080p) of its own sample, on its own contrast side (polarity 0 takes the stronger at the samples), so it never takes the other side of white tape, a truss's other chord or the opposite-contrast boundary. Either way the curve is then fitted twice to the edge peaks within the window of it (`_Band.track`: first to the half of the peaks it fits best, so a stretch where another edge runs beside the line cannot pull it over, then to every peak within `_TRACK_TOLERANCE`), and each point takes the strongest peak within `_POINT_TOLERANCE` of the curve; a hand-traced line's ends stay within their reach of the clicks. **All five points take one polarity**, otherwise gaffa tape's width reads as curvature. A point without a peak above `_MIN_EDGE_STRENGTH`, or above `_NOISE_FACTOR` times the band's own gradient noise (the median absolute gradient scaled to a sigma), stays on the curve inside the picture, is reported `snapped=False`, and the wizard starts a middle point like that switched off; a peak must stand at least as high as both its neighbours, so the edge of a window on the flank of an edge beyond it is none. **A line where fewer than two points find a peak stays exactly where it was placed**: the best curve over grain is still a curve. Cells outside the snapshot carry no evidence (masked from the geometry, since a canvas paints nothing there). The worst case, a full-width hand-traced line under the top edge over noise, takes about 0.2 s on the Mac.

**Edge suggestions** (`find_edge_candidates`) spare the operator the tracing: on entering the Lens step the wizard sends the snapshot's luma scaled under `EDGE_MAP_WIDTH` (`edge_map_scale`, mirrored by `lensEdgeScale()` and pinned by a test; a 720p snapshot goes whole, a 1080p one at half size, about 700 kB to 900 kB) and draws what comes back as faint dashed polylines; a tap turns one into a line from its five arc-length samples, which the band snap then refines at full resolution, and a deleted line gives its suggestion back. The server finds thin edges (5-tap blur, central gradient, non-maximum suppression, the weak threshold `_WEAK_EDGE`) **and thin lines** (`_thin_ridges`: the principal curvatures of a 3-tap-blurred image, the stronger less the weaker so a blob scores nothing, scaled by `_RIDGE_TO_EDGE` so a line and a step of one contrast score alike, and only where the ridge beats the gradient, which the flanks of a step never do; a soft 720p camera shows the seams between stage decks as one-pixel lines of about 25 luma that no gradient sees, and sees them only at full size, which is why the map width is 1280), follows every marked pixel into a chain along the local direction (strongest seed first, each pixel once, a step must point `_FOLLOW_COSINE` along the direction, which is the edge's tangent steadied by the step taken), cuts a chain where the chord before a point and after it turn by `_CORNER_ANGLE` (`_split_at_corners`), trims `_END_TRIM` (a corner window, so a hook into a crossing goes too) off each end, keeps a piece that **bows like a line** (within `_SMOOTH_RMS` of one quartic, since a parabola misses the wave a corner term puts in a line, with a curvature under `_MAX_CURVATURE_WIDTH` divided by the scaled width: a 100° lens bends a straight line to about 2, a spotlight's rim is 20 and more; and straying from its own chord by no more than the slider ends bend that chord where it runs, with the lens centre at the picture's centre or on the edge of its bound, times `_SAG_MARGIN`, since a wide arc, a round truss or a curved stage front away from the frame edge, is gently curved at its middle too, but strays further), **joins collinear pieces across gaps** under `_JOIN_GAP_FRACTION` of the width (`_join_across_gaps`: ends within the gap, each piece running on toward the other within 20°, the two together still bowing like a line and the second stepping aside from the first by no more than `_JOIN_OFFSET` scaled pixels where they meet (`_join_offset`: the step one quartic through both needs there; a thin line's crest and its two flanks lie within it, while a riser's seam that runs on a few pixels beside a deck's seam is another line, and joined into one suggestion it bends the snapped line), nearest first, never into a ring; a tape line is cut at every crossing of the grid and a stage edge at its stairs; each end meets only the ends in its own and the touching cells of a grid one gap wide, since a textured picture, an LED wall or a perforated panel, has thousands of pieces), and keeps what is at least `_MIN_LENGTH_FRACTION` of the scaled width and reaches `_STRONG_EDGE` somewhere. Pieces are ranked by the **square of their length** (a line's bow grows with it), distance from the centre (a line far out shows the lens most) and the square root of their mean strength capped at `_CLEAR_EDGE` (brighter than clear is not better: the PA stacks must not outrank the deck seams); one that repeats an accepted piece (`_DUPLICATE_FRACTION` of its points within `_DUPLICATE_DISTANCE` snapshot pixels: the two edges of a strip of tape, the top and bottom of a stage trim) or **runs alike** beside one (middles within `_CROWD_DISTANCE_FRACTION` of the width, directions within 15°: the stair treads under a stage edge, which all say the same about the lens) is skipped, and at most `MAX_CANDIDATES` are returned. Whether a suggested edge is straight in reality is the operator's call; the misfit check catches one the other lines disagree with. `tests/test_lens_calibration.py` runs the whole step on synthetic stages rendered through known lenses with the overlay's own inverse (`tests/_lens_scene.py`), a 720p deck scene with one-pixel seams included, and expects the pair back within 0.01; on a stage whose seams run on up a riser a few pixels aside, every suggestion must be straight through the true lens.

**Routes** `POST /api/wizard/lens/snap` (endpoints + the base64 luma band, and for a used suggestion `near`: its five samples and polarity → five points with their marks), `POST /api/wizard/lens/edges` (the scaled luma → candidates with their polyline, five samples, length, strength and polarity, plus the edge map as bytes when `with_map` is `true`) and `POST /api/wizard/lens/fit` (lines of active points and the lens centre `cx` / `cy` to hold → k1, k2, `k2_fitted`, per-line RMS / misfit / predicted curve / dropped points, rating, hint; at most `MAX_LINES` lines of `MAX_POINTS_PER_LINE` points) all answer 400 on malformed bodies like the other wizard routes. They read numbers strictly (`_json_number` / `_json_int` / `_json_point`: no booleans, no strings, counts whole), and the edges route takes only the scale the wizard scales that snapshot by (`edge_map_scale`), so a request cannot buy a larger map than the wizard sends. **In the wizard**, lines live in the session (`lensLines`) as endpoints plus middle points in the line's frame `(t, off)`, so an endpoint move carries every middle point along with its chord, and a middle point goes wherever it is dragged or moved with the arrow keys, along the line as well as across it; the fit runs debounced after every release, an edit drops the answer to any fit already sent (`lensFitSeq`), and a failed fit leaves no earlier result standing; a snap answer lands only on a line still as it was sent; a used suggestion is snapped between its first and last sample with `near`, sent only when its samples lie inside the band the station searches (`lensNearFits`; one bowed past it keeps its samples, unsnapped), and no other snap carries it; a **Not usable** fit, or one with a line that does not fit the others, is shown but not applied (`lensFitApplies`), since its lens is whatever the lines cannot pin down or what the bent line pulled it to; the lens stays as it was, Review names the rating "…, not applied" until the pair is changed under User input (`lensHandTuned`), and the coverage hint is shown in the hint box only, never under the result; every fit sends the centre in use and an applied fit writes only its pair, the answer's `k2` also when `k2_fitted` is false, which the result line marks "(estimated)"; the result line names that centre when one is set, in whole pixels of the snapshot ("lens centre 13 px left, 9 px up", an axis that rounds to 0 px left out), and a centre typed while lines are traced measures them again; a line spanning less than `LENS_MIN_SPAN_PX` (mirroring `_MIN_LINE_SPAN_PX`) does not count; a tap is judged in CSS pixels; refreshing the snapshot keeps the lines unless the resolution changed. The browser cuts the band with each cell's centre on the pixel position the server models (a canvas puts pixel centres at +0.5 on both sides of the transform), and scales the edge map by block means (`lensScaledLuma`), which is what the tests model and what keeps a one-pixel seam past a scale of three. The sliders under the result and the **Lens centre** row (**Right of the picture centre (px)**, **Above the picture centre (px)**, whole pixels of the snapshot, ±`floor(C_BOUND · D)`) are **User input**; the page keeps the centre in half-diagonals (`S.lensCentre`), so a snapshot of another size shows it in its own pixels, and a centre field without a whole number in range keeps the lens from being saved (`wizLensValid`; Save and finish names the centre, `wizLensSaveError`): the last centre taken stays in use, and the field keeps its text and flag across a snapshot of the same size. A range error shows once its field is left or committed; the limit error shows while typing. The pair's error shows while the pair alone falls short, else the centre's. Each open suggestion carries a bubble (`lensPlaceBubbles`, `lensBubbleOutline`, in CSS pixels over the picture in `#lens-tails` / `#lens-bubbles`): the check uses it (snapped by the station like a tapped line), the cross rejects it, and a rejected suggestion stays away, matched by its ends on every new snapshot, until the Lens step's **Refresh Image** (`lensRefreshImage`). The hint box above the picture (`renderLensHint`) names the one next thing to do and is mirrored in the full-screen toolbar. **Load lens calibration** sets the lens from one saved on this station (`GET /api/wizard/lens/calibrations`) or from `camera.lens_k1` / `lens_k2` / `lens_cx` / `lens_cy` of an exported settings file, read in the browser (`lensFromSettings`: a missing centre is 0, a value that is no finite number or that the station would clamp or pull back refuses the file); its list and the loaded line name a centre that is not 0; it removes the lines on the picture, and a later fit rated above Not usable replaces it. **Save lens calibration** posts a name, the pair and the centre (`POST /api/wizard/lens/calibrations`, at once, independent of Save and finish), plus `width` / `height` of the snapshot when one has loaded: both or neither, whole numbers in `1..16384` (`lens_calibrations.MAX_SIDE`, the bound `_require_wizard_canvas` uses too), else 400. ## Camera calibration from marks (`scene/calibration_points.py`)

Calibration is **web-only**: the Setup Wizard's Camera Calibration step posts marks to `/api/wizard/solve`. A **mark** is a known point (typed X / Y / Z) or a triangulated one, which the page calls a distance point (its distances to two other marks plus its Z), with a pin on the snapshot. Simple's marks are the rectangle's corners, known marks with ids 1 to 4 in `CALIBRATION_CORNERS` order (DSL, DSR, USR, USL); Advanced's are the operator's own, at most `MAX_CALIBRATION_MARKS` (12). A triangulated mark must be pinned (two distances leave two places, mirrored across the line between its marks); a known one may stay unpinned and still anchor others.

**One fit, both modes.** `solve_marks` runs a Levenberg-Marquardt fit (`_fit`) of the 7 camera values plus every triangulated mark's x, y, against the pins (`PIXEL_SIGMA`, 1 px) and the triangulated distances (`DISTANCE_SIGMA`, 4 cm), each residual in its own sigma; the camera columns of the Jacobian by central differences, each mark's x, y in closed form. It needs four pinned marks (7 unknowns, 2 equations per pin). Every pin counts the same and no mark is left out: one that disagrees shows in its error and in the caution.
- **Seeds** (`_seeds`): with a camera position (`hint`), that position looking at 0/0/0, roll 0, at the saved FOV and at `SEED_FOVS` (40° and 90°); with four pinned known marks at one height (within 1 cm, no three in a line, `_level_quad`), the homography decomposition. Simple has the second unless its decomposition gives none, Advanced always the first. Without a camera position, when that decomposition gives nothing (near straight down it decomposes to noise or to none) or a camera steeper than `STEEP_PITCH`, the camera is also seeded above the pinned known marks' centre (`_above_marks`), at the entered height or as high as the pins' spread says at the saved FOV, looking down at `NADIR_PITCH` (-89°) at the four `STEEP_TURNS` bearings. Not with a camera position: there it bought nothing and a narrow lens fitted to a wrong camera from it.
- **Triangulated marks** start at their trilateration (`trilaterate`), chained after the marks they are measured from (`_order`); circles that miss by up to `MEET_TOLERANCE` (`3 √2 · DISTANCE_SIGMA`) meet at their closest approach, more leaves the mark unplaced with its `REASON_*` sentence. Of the two mirror places the seed camera's view of the pin picks one.
- **Mirror sides**: every seed is fitted `SCOUT_ITERATIONS` twice, with the pin-picked places and with all of them flipped; an upright camera (at or above the lowest mark, pitch ≤ 0) beats one that is not, then the lower cost wins, and only the winner is fitted to `FIT_ITERATIONS`. A fit with no finite answer or a FOV outside 10-170° is `NO_FIT`.
- **Camera height**: from almost straight above, flat marks cannot tell the camera's height from its FOV, and a camera steeper than about -85° can come out metres off with nothing in the errors. An entered `height` (m) starts every seed at it and joins the fit as one more residual, `(z - height) / HEIGHT_SIGMA` (1 cm), last in the residual vector; its Jacobian row comes with the camera columns' central differences (exact for a linear row) and is zero in the mark columns. `MarkSolve.steep` is `pitch < STEEP_PITCH` (-82.5°): the route answers it as `steep`, so the page never mirrors the rule. With a height entered, a height not above the lowest pinned mark, or no camera at all, is `NO_FIT_AT_HEIGHT`, which names the height. The floor-reach check (`floor_off`) is skipped when the fit or the level marks' camera is steeper than `STEEP_PITCH`: there the four marks' homography moves the camera metres for a pixel, and the height holds the fit instead. The page asks for the height in its own blue box while the answer is steep, keeps the field while it holds text, and a missing height never blocks Save and finish nor joins the caution.
- `stale` is asked before every iteration and raises `SolveSuperseded`.

**Plausibility** (`plausibility`) returns the caution's reasons as data the page words in its units, and never blocks Save and finish: the camera further from the entered position than `max(1 m, 10 %)` of its distance to the marks' centre (Simple, the whole gap) or any axis further than `max(2.5 m, 10 %)` (Advanced); a FOV outside 20-120°; a camera below the lowest mark; a camera looking up; a pin more than `FLAG_PX` (5 px) from where the camera sees its mark; a triangulated mark's distance off by more than `FLAG_DISTANCE_M` (3 σ). The page adds "The lens was not measured" in Simple with `lens_distortion` on when nothing was measured, loaded or typed under User input in this run and the station's saved pair is 0 / 0: four coplanar points fit exactly whatever the lens.

**The route** reads the body strictly (`_wizard_marks`: the config's own `problem()` rule per mark, ids unique, Simple's marks its four corners, `calibration_mark_drops` for a From that is missing or loops back; `hint` and `camera_height` (a number or null) within `MARK_REACH_M`; `saved_fov` in 1-179), so a mark the Setup Wizard can solve with is one it can save, and answers 400 on any of it. A body naming its page (`solve_page`, `solve_seq`) is recorded as that page's newest solve before the rest is read (`_WizardSolveTurns`, one per server, the last 64 pages); an older one is refused with 409 before any work, and a fit the page has stopped waiting on answers 409 too. While the solve cannot run it answers 422 with `need` (the camera position in Advanced, known marks in Advanced, pinned marks), worded as the page words them. Pins arrive in snapshot pixels and are undistorted with the request's lens (`invert_overlay_distortion`, the centre included); each mark's `seen` is bowed back for the page. The answer: `camera`, per mark `{id, position, reason, seen, error, distance_error}`, `count`, `largest_error`, `steep`, `reasons`; or 422 with `NO_FIT` (`NO_FIT_AT_HEIGHT` with a height) and the marks.

**Config** (`CameraConfig.calibration_mode`, `calibration_marks`, `calibration_height`): see [config](config.md#sub-config-notes). Written only by the Setup Wizard's Save and finish (the Operator Screen's Ctrl/Cmd+S writes the pose alone), listed read-only on the Camera form, carried into the diagnostics bundle by its config dump, and read by nothing at runtime: the solved pose is what the HUD uses.

## Peer authentication (`web/peer_auth.py`)
Peer-to-peer config broadcast is HMAC-signed. The web PIN is the HMAC key; the PIN itself never leaves the host.

- **Signature headers:** `X-Auth-Signature` (hex HMAC-SHA256) + `X-Auth-Timestamp` (unix seconds).
- **Signed payload:** `method\npath\nSHA256(body)\ntimestamp` – path includes the query string when present, so a query is semantically bound to the signed operation.
- **Timestamp window:** `TIMESTAMP_WINDOW_SECONDS = 30` – tolerant of typical NTP-free LAN skew, too narrow for offline replay to be practical.
- **Pre-auth body cap:** `_check_auth` requires `Content-Length` and rejects requests over `peer_auth.MAX_SIGNED_BODY_SIZE` (1 MiB) with 413 before reading – the verifier has to hash the full body before the HMAC proves the sender, so an unauthenticated client could otherwise force an unbounded spool.
- **The PIN never travels:** a third-party script authenticates by cookie (browser flow) or signs with `peer_auth.sign()`.
- **Host binding not included:** OpenFollow only performs broadcast-to-all operations and restricts targets to private IPs (`_is_private_peer_ip`), so cross-peer replay produces only the same effect a legitimate broadcast would have.
- **Offline brute-force note:** a captured signed request lets an attacker test candidate PINs offline. The HMAC construction only hides the PIN from the wire – it does not make a short / low-entropy PIN strong. Operators wanting meaningful resistance should use a longer shared secret; a future KDF derivation would raise the cost further.

## Browser auth (`_check_auth` + `login_submit`)
- `web_pin` non-empty → every non-asset route requires either a valid HMAC signature (peer path above) or the `_openfollow_auth` cookie.
- Cookie is set with `httponly=True`, `path="/"`, **`samesite="strict"`**. Strict blocks the browser from attaching the cookie to any cross-site request, which defeats CSRF without a separate token layer. OpenFollow is LAN-only so the reduced cross-site ergonomics are acceptable.
- `/login`, `/assets/*` and the About pages are exempt from auth. The login page shows no station state.

## Refused names and failed saves (`_check_auth`, `static/js/save-feedback.js`)
- **A change through a name the station does not accept** (an `Origin` / `Referer` host outside `_allowed_request_hosts()`, the CSRF / DNS-rebind defence) is answered by `_refused` in the shape its caller reads: JSON `{error, action, href}` for HTMX and script requests, and a page for a plain form post (`_is_navigation`: `Sec-Fetch-Mode: navigate`, else `Accept: text/html` without `HX-Request`) – the login page with the reason where "Incorrect PIN" sits, or `refused.tpl`. Never Bottle's bare 403 page.
- **The address offered** is the local address the connection arrived on (`SERVER_ADDR`, recorded by `_QuietHandler.get_environ`): the browser just reached it, and no DNS lookup is involved. Loopback (a proxy on the box) offers none.
- **On page load**, every full page (index, wizard, login, about) spreads `_page_host_context()`, so a page opened through such a name shows the red banner before anything is edited. The `Host` header decides it; the refusal stays the backstop, because a reverse proxy can make `Host` and `Origin` disagree.
- **Every save reports failure the same way** (`window.OpenFollow.saveError`): the form's ring flashes red for 0.55 s like the green save flash, and a red line under its actions says what the station observed plus one next step, until the next edit or save. Non-GET HTMX requests are covered globally (`htmx:responseError` / `htmx:sendError`); a script-driven save calls `saveError.show(box, info, lead, near)`. A dialog that closed before its request failed hands the line to the section last clicked. Don't add toasts, alerts or modals for a failed save; the offline update upload keeps the updater's own dialog, and the save to a USB storage device ends its dialog on the export's result (a refused start still reports through `saveError`). `tests/test_save_feedback.py` fails a template or input plugin that saves by script without the helper.

## Login throttle (`web/login_throttle.py`)
Per-IP exponential-backoff lockout on PIN authentication. Without this, a 4-digit PIN is exhausted in seconds over a LAN – no rate limit, no attempt counter, no back-off.

- **Curve:** 1 s after the first failure, doubling each subsequent failure (1, 2, 4, 8, 16, 30 …), capped at `_MAX_LOCKOUT_S = 30 s`. The exponent saturates at 60 to keep `2 ** n` inside float range under sustained probing – without this an attacker could drive `failures` past 1024 over ~8.5 hours and turn brute-force traffic into server 500s via `OverflowError`.
- **Two vectors, one throttle:** `setup_routes` builds a single `LoginThrottle` instance shared by `POST /login` (form path) and the peer-auth signature verifier in `_check_auth`. An attacker can't sidestep the lockout by alternating between vectors. The lockout check runs **before** any HMAC compute on the peer path, so a flood of bogus signatures can't keep the verifier hashing.
- **Reset on success:** a correct PIN check (`record_success`) clears that IP's history. Idle entries (no failure within `_RESET_AFTER_S = 10 min`) get GC'd by both per-IP cleanup in `remaining_lockout` and a periodic full sweep in `record_failure` (amortised O(1) per call) – required because an attacker rotating through one-off IPs would otherwise grow `_entries` without bound.
- **`_is_stale` requires both conditions:** an entry is collectable only when the idle threshold has passed *and* `lockout_until` has expired. Defends against a misconfigured `reset_after_s < max_lockout_s` where the per-IP GC could otherwise drop an entry mid-lockout, letting an attacker reset their failure count by waiting one idle window.
- **Wire response:** locked-out callers get `429 + Retry-After: <seconds>`. The header is computed via `math.ceil(remaining)` so it never overshoots the cap (`int(remaining) + 1` would advertise `31` on a `30 s` cap). `bottle.abort()` discards thread-local response headers, so the 429 is raised as `HTTPResponse(headers={"Retry-After": …})` directly – not via `abort()`.
- **Threading:** every public method takes the instance lock, and `now = self._clock()` is read **inside** the critical section so a contended caller can't compute `lockout_until = now + delay` against a stale timestamp.
- **Keyed on the connection, never a header:** the address is `_client_address()`, the WSGI `REMOTE_ADDR`. Bottle's `request.remote_addr` takes a client-set `X-Forwarded-For` first, so a client could present a fresh address per guess and never be locked out; do not use it for anything that decides access.
- **No reverse proxy on the station:** behind one, every client connects from loopback and shares one lockout. That deployment is not supported.
- **Per-IP, not per-account:** acceptable because there is only one shared PIN. Legitimate users behind the same NAT share lockout – a known trade-off on a LAN show network. No persistence across server restarts; matches the LAN threat model.
- **Coverage:** 100% line + branch in `tests/test_login_throttle.py` (mock-clock unit tests, including thread-safety stress) + integration tests in `tests/test_web_server.py` (live server, real `urllib`, both vectors). Module is in the `mypy --strict` batch.

## Broadcast target restriction
`_send_config_to_peer` / `_send_config_import_to_peer` refuse to POST to non-private IPs – `ipaddress.IPv4Address.is_private` covers RFC 1918, link-local, and loopback, which is the set a legitimate peer can plausibly have. Closes the SSRF vector where a crafted beacon advertised an attacker-chosen endpoint (e.g. `web_port=22` or an internal service port).

## Service name as an argument
`_is_valid_service_name` rejects any value starting with `-` as well as anything outside its pattern, so `update_service_name` can never be parsed as a `systemctl` option; an invalid name falls back to the default unit (`_service_unit_name`).
