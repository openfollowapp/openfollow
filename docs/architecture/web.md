# Web UI

Covers `web/`: routes, auth, peers, the Setup Wizard. The rules that apply everywhere are in [CLAUDE.md](../../CLAUDE.md).

## UI copy: explanations live in the help drawer (REQUIRED)

**Do not add inline help to web forms.** A `<label>` (plus a `placeholder` where
one genuinely helps) is the whole of a control's inline copy. Everything else –
what the setting does, when to use it, defaults, side-effects, caveats, examples,
and "manage X under Y" pointers – goes in that section's **help drawer markdown**
(`openfollow/web/help/<section>.md`, surfaced by the per-section `?` drawer via
`data-help="<section>"`).

- **A new `field-note` is a review blocker**, including a terse one-line pointer.
  "For a camera looking from upstage", "Comma-separated; e.g. …", and
  "Manage destinations under OSC Destinations." have all been stripped on sight.
  If the label alone doesn't identify the control, fix the label.
- When you add or change a control, update the matching
  `openfollow/web/help/<section>.md`. The help drawer is the single home
  for the explanation, so it can't drift between the form and the docs.
- The same goes for `title` tooltips carrying explanation. A `title` is fine for
  a badge or icon with no visible label (e.g. the "This session" interface badge).
- Existing `field-note`s predate this rule – leave them where they are unless you
  are already editing that block, then move the text into the help `.md`.
- `section-note` (the one-line subtitle beside a section's `<h2>`) is a *name*,
  not help: "Marker speed limits, default speed, and default position" is fine;
  a sentence teaching behaviour is not.

## Setup wizard (`/wizard`)
Guided workflow for camera positioning and grid calibration, seven steps, eight with the experimental **Lens** step:
1. **Preparation** – info + SVG stage layout illustration
2. **Grid Setup** – the displayed unit system first (shared with General; a change reloads into the step, lengths kept in metres, and is refused while a length does not read), then width, depth, z_offset, spacing, x_offset, y_offset; dynamic SVG illustration updates from input
3. **Video Source** – select and configure camera input (reuses video source UI); saved before moving on. Carries the Video Source panel's failure box, polled only while it shows (`[this.offsetParent !== null]`)
4. **Lens** (only with `ui.show_experimental_features`) – measure `lens_k1` / `lens_k2` from lines that are straight in reality (see "Lens distortion from straight lines" below); skipping keeps the current pair. `ui.developer_mode` (config-only, no form control) adds a **Show edges** checkbox that lays the edge map the suggestions were picked from over the snapshot
5. **Camera Position** – pos_x/y/z, pitch/yaw/roll, fov; dynamic isometric illustration
6. **Reference Mapping** – draggable marker for coarse calibration (single known point); rigid-body shift of all corners. **Fine adjust** swaps in one 4× crop around the Reference Point, dragged and nudged like a Corner Pinning box
7. **Corner Pinning** – 4 draggable corners, DLT solve, solved camera params displayed. The grid's inner lines are drawn inside the quad as the HUD draws them (`wizGridLines`: the undistorted corners fix the plane's homography, the lens bows each line again, the line count mirrors `overlay_draw_scene.grid_line_count`), so they follow a dragged corner. Every point the wizard drags (Lens, Reference Mapping, Corner Pinning) is the Lens step's dot (`pointHandle`), and dragging one in a full view shows the shared loupe (`showLoupe`: a 4× look at the full-resolution snapshot beside the finger). A corner nothing drags (Reference Mapping, Review) carries no marker, and corner labels sit diagonally outward from the grid's centre
8. **Review & Apply** – read-only summary of all values + green overlay with the grid's lines; Apply or Discard

Key implementation details:
- **Steps are keyed, never numbered, in script.** The template builds the step list (`_steps`, the Lens step only with the toggle) and publishes it as `window.WIZ` (key → index) and `WIZ_STEPS`; step content divs are `#wizard-step-<key>`, nav buttons call `wizardNext()` / `wizardPrev()`, and the session stores `_stepKey`. A step inserted or left out shifts nothing
- **The script's maths is tested by running it.** `tests/test_wizard_js.py` pulls named functions out of `wizard.tpl` (`tests/_wizard_js.py`, by brace matching) and runs them in node against the Python they mirror: the grid lines against the HUD's, the lens warp, its inverse and the fold check, the band and edge-map geometry, the loupe's placement and the imperial length read. It skips where node is not installed. A function it calls must stay pure: pass in what it reads from the page
- Server-side projection/unprojection via `/api/wizard/project` and `/api/wizard/unproject` to avoid JS↔Python coordinate math mismatches
- SVG viewBox matches native image resolution so coordinates map 1:1 regardless of CSS scaling
- `sessionStorage` persists wizard state across accidental navigation/refresh
- Touch-friendly: 44 CSS px hit areas, `touch-action: none`. The viewBox is the snapshot's resolution, so handles, labels and strokes are sized in CSS pixels (`overlayPx`, `vector-effect: non-scaling-stroke`) and drawn again on a resize
- An imperial length field carries the metres it shows in `data-meters`; while its text is those metres formatted, `wizReadLen` returns them, since ft / in text rounded to 0.01 in reads back with a residue (0.5 m as 0.500126 m, a grid line more)
- The Lens step works from the keyboard: suggestions are buttons (Enter adds one), every point has an `aria-label`, a focused point is the selected one, and Delete leaves the focus on the next line or the picture
- Keyboard arrow support for draggable points (debounced at 300ms)
- DLT-solved values back-propagate to form fields when navigating back; the form is the one camera Review and Apply read
- Drag handlers (`setupCornerDragging`, `setupRefDragging`, the zoom boxes) are bound once at page load on groups that outlive every redraw; a redraw keeps the keyboard focus on its handle. A handler bound per projection acts once for every projection so far
- `restoreFromSession` returns true whenever it restored a session, so the Y Offset default for a fresh visit never overwrites restored values; a step key this page lacks starts at Preparation, and lens state is restored only in the shape the page draws
- Finish uses JSON API (`/api/config/camera`, `/api/config/grid`) to avoid resetting unrelated bool fields; `applyAndFinish()` must check each response's `.ok` before clearing session + redirecting (silent-drop regression guard in `tests/test_wizard.py`)
- **Input validation:** `/api/wizard/{project,unproject,solve}` must return 400 – not 500 – on malformed bodies. All float coercion and shape checks (including numpy array construction from caller-supplied coords) belong *inside* the try/except. Shared `_wizard_camera_params()` helper validates the 7-field camera vector, and `_require_wizard_canvas` refuses a canvas side outside `(0, 16384]` (a canvas of 1e170 overflowed the Lens snap into a solve that never returned)
- **Step nav semantics:** `<nav aria-label="Setup wizard steps">` landmark with `aria-current="step"`, **not** `role=tablist`/`role=tab`. A tablist without `aria-selected` / `aria-controls` / `role=tabpanel` is an incomplete ARIA tab pattern; for a linear wizard, nav + aria-current is the correct lighter-weight semantics
- Snapshot blob URLs: `loadSnapshot()` must revoke the previous `URL.createObjectURL` after the new image loads to avoid a per-refresh memory leak
- "No feed" UX: each preview container has a sibling `.wizard-no-feed` placeholder div; `setPreviewVisibility()` toggles both so the snapshot steps never render blank when `/api/video/snapshot/full` fails

## Lens distortion from straight lines (`scene/lens_fit.py`, `scene/edge_snap.py`, `scene/edge_chains.py`, `lens_model.py`)

**The operator never reads `k1` or `k2`.** Every label, result line, hint and help paragraph calls the pair **Barrel / fisheye** (`lens_k1`) and **Edge fit** (`lens_k2`); the field names, the API keys and the code keep the coefficient names.

The overlay correction is `f = 1 + k1·r² + k2·r⁴` about the image centre, `r` normalised to the half-diagonal (`r = 1` at a corner); `project_points` / `unproject_to_plane` stay pinhole, `apply_overlay_distortion` bows what the HUD draws and `invert_overlay_distortion` undistorts clicks, detection pins and zone feet. **The one validity rule is the fold check**, `lens_model.lens_warp_is_valid` (stdlib-only, because `configuration.py` reads it): `r·f(r)` must keep growing on `[0, 1]`, i.e. `1 + 3·k1·s + 5·k2·s² > 0` for `s ∈ [0, 1]`, closed form in `lens_fold_radius`. There is no box: a 100° lens on 16:9 sits near `(-0.47, 0.25)`; only a coefficient past 1e3 is refused outright, where `9·k1²` would overflow. The rule is about **pinhole** radii: under barrel the warp takes the frame corner to `f(1) < 1`, so a screen point beyond what the warp reaches has no preimage and lands on the fold ring (a pair fitted without its edge term can leave a band along the frame's edge like that). `CameraConfig.__post_init__` falls a folding pair back to `0 / 0` with a WARNING, the Camera form checks the pair through `validate(..., context=)` whenever either field or either slider changes (each lens input's `hx-trigger` adds `change from:` the other three, since a slider writes its field without a blur), reading an empty sibling as its saved value as the save does (`needs_cfg`), and refuses it, `_wizard_lens_coeffs` falls back to pinhole, and the fit never leaves the valid region. The inverse is a **bracketed Newton solve** (`invert_normalised_radius`, broadcasting radii against a grid of pairs) exact over the whole valid range: it stops once every radius settles, after at most 40 steps, since just above `k2 = 9·k1²/20` the warp's slope nearly touches zero past the frame and Newton creeps (about 24 steps); a distorted radius the warp never reaches lands on the fold radius. `wizard.tpl` mirrors the fold check and the inverse (`wizLensFoldRadius`, `wizInvertRadius`) for its bowed edges and live curves.

**The fit** (`fit_lens_from_lines`) is the plumb-line method: each traced line's active points are undistorted and measured against their own total-least-squares line, its direction taken from the line's first point toward its last (the SVD's sign is free, and one that flips between the Jacobian's two samples flips every residual); the cost is the sum of squared perpendicular residuals. A coarse grid over both coefficients (vectorised through `_Lines.grid_cost`, closed-form smallest eigenvalue of each line's scatter) seeds a damped Gauss-Newton refinement, because a start at zero diverges on strong barrel distortion. **k2 is only fitted when its predicted sigma is below `K2_SIGMA_GATE`** (0.05, needs lines near the corners), else it stays `0` and the k1-only solution is reported. The rating is the predicted uncertainty of the warp at the frame corner in px, from the full 2×2 covariance with the residual sigma floored at 1 px, or, when larger, how far apart the fit and another minimum the seeds reached put a point out to the corner, if that minimum's cost is within `_RIVAL_MARGIN` residual variances of the best (the 95 % region of a two-parameter fit). The covariance sees only its own minimum: traced along the top and bottom edges alone, a strong barrel lens and one about 0.15 weaker fit the points equally well, some 25 px apart, and either rated excellent. `RATING_THRESHOLDS_PX` (2.5 / 5 / 10 / 20 → excellent / good / okay / medium, else low) are fixed from simulation and pinned in `tests/test_lens_fit.py`; the hint names the emptiest edge band, or the missing corner line. A line **does not fit the others** when, with k1 refitted without it (k2 held, so two remaining lines cannot be overfitted), its RMS exceeds 3 px, three times the others' RMS, and three times the displacement the refit's own k1 uncertainty predicts at that line (`_k1_variance`, the residual sigma floored at 1 px); the last term is what keeps the one line carrying the curvature from being convicted by the lines that cannot pin k1 down without it. Needs three lines. Zero coefficients reproduce the pinhole path exactly.

**Edge snap** (`snap_line_to_edges`) runs on a luma band the browser cuts along the traced chord (`lensBand()`: one canvas `drawImage` with a rotating transform, so the server never needs the JPEG decoded and the snapshot the operator sees is the one measured): one column per `band_step` pixels of the chord, one row per pixel across it, `band_half_size` rows to either side, both mirrored by the wizard and pinned by a test. A straight edge seen through a lens bows by far more than any search around the chord's own points could cover (the stage edge in a wide shot sat 60 px off its chord), and with a strong lens the bow is not even one arc: the r^4 term pushes the ends of a line near the frame edge out while the r^2 term pulls its middle in. So the band is searched for the **highest-scoring smooth path** through all its columns (dynamic programming over the signed luma gradient, each column clipped at `_GRADIENT_CLIP` so one bright crossing cannot carry it, at most `ceil(_PATH_SLOPE × step)` rows of climb per column and `_PATH_BEND_PENALTY` per row so it runs straight across a gap), the path is smoothed by the shape a straight line can take through a radial lens (the bows of the r^2 and r^4 terms, drawn with `_REFERENCE_K1` / `_REFERENCE_K2`, plus a shift of either end, fitted by least squares weighted by the path's evidence; the references are pincushion because a barrel reference folds before the corners), and each point then takes the gradient peak within `_POINT_WINDOW` of the curve. **The clicks are authoritative for the ends**: both ends of the path, the fitted end shifts and the end points' own peak search stay within `end_search_radius` of the clicks (16 px at 1080p, about 8 px on a laptop screen showing the snapshot), and the whole path is confined to a **corridor** around the chord that is that reach plus `_CORRIDOR_K1` / `_CORRIDOR_K2` reference bows, the bow of any lens the fit accepts. The corridor keeps a brighter parallel edge further off (the next stair tread, the next strip) from winning the path in the middle and dragging the ends to their limit; a click more than the reach off its edge gets unsnapped ends to drag, not a line on another edge. **All five points take one polarity** (the sign whose path scores higher), otherwise gaffa tape's width reads as curvature; a point without a peak above `_MIN_EDGE_STRENGTH`, or above `_NOISE_FACTOR` times the band's own gradient noise (the median absolute gradient scaled to a sigma), stays on the curve, is reported `snapped=False`, and the wizard starts a middle point like that switched off. A peak must stand at least as high as both its neighbours, so the edge of an end's window on the flank of an edge beyond its reach is none. **A line where fewer than two points find a peak stays exactly where it was clicked**: the best path through grain is still a path, and following it moved points up to the full reach. Cells outside the snapshot carry no evidence (masked from the geometry, since a canvas paints nothing there).

**Edge suggestions** (`find_edge_candidates`) spare the operator the tracing: on entering the Lens step the wizard sends the snapshot's luma scaled under `EDGE_MAP_WIDTH` (`edge_map_scale`, mirrored by `lensEdgeScale()` and pinned by a test; a 720p snapshot goes whole, a 1080p one at half size, about 700 kB to 900 kB) and draws what comes back as faint dashed polylines; a tap turns one into a line from its five arc-length samples, which the band snap then refines at full resolution, and a deleted line gives its suggestion back. The server finds thin edges (5-tap blur, central gradient, non-maximum suppression, the weak threshold `_WEAK_EDGE`) **and thin lines** (`_thin_ridges`: the principal curvatures of a 3-tap-blurred image, the stronger less the weaker so a blob scores nothing, scaled by `_RIDGE_TO_EDGE` so a line and a step of one contrast score alike, and only where the ridge beats the gradient, which the flanks of a step never do; a soft 720p camera shows the seams between stage decks as one-pixel lines of about 25 luma that no gradient sees, and sees them only at full size, which is why the map width is 1280), follows every marked pixel into a chain along the local direction (strongest seed first, each pixel once, a step must point `_FOLLOW_COSINE` along the direction, which is the edge's tangent steadied by the step taken), cuts a chain where the chord before a point and after it turn by `_CORNER_ANGLE` (`_split_at_corners`), trims `_END_TRIM` (a corner window, so a hook into a crossing goes too) off each end, keeps a piece that **bows like a line** (within `_SMOOTH_RMS` of one quartic, since a parabola misses the r^4 wave, with a curvature under `_MAX_CURVATURE_WIDTH` divided by the scaled width: a 100° lens bends a straight line to about 2, a spotlight's rim is 20 and more; and straying from its own chord by no more than `_MAX_SAG_FRACTION` of it, since a wide arc, a round truss or a curved stage front, is gently curved at its middle too, but sags a quarter of its length), **joins collinear pieces across gaps** under `_JOIN_GAP_FRACTION` of the width (`_join_across_gaps`: ends within the gap, each piece running on toward the other within 20°, the two together still bowing like a line, nearest first, never into a ring; a tape line is cut at every crossing of the grid and a stage edge at its stairs; each end meets only the ends in its own and the touching cells of a grid one gap wide, since a textured picture, an LED wall or a perforated panel, has thousands of pieces), and keeps what is at least `_MIN_LENGTH_FRACTION` of the scaled width and reaches `_STRONG_EDGE` somewhere. Pieces are ranked by the **square of their length** (a line's bow grows with it), distance from the centre (a line far out shows the lens most) and the square root of their mean strength capped at `_CLEAR_EDGE` (brighter than clear is not better: the PA stacks must not outrank the deck seams); one that repeats an accepted piece (`_DUPLICATE_FRACTION` of its points within `_DUPLICATE_DISTANCE` snapshot pixels: the two edges of a strip of tape, the top and bottom of a stage trim) or **runs alike** beside one (middles within `_CROWD_DISTANCE_FRACTION` of the width, directions within 15°: the stair treads under a stage edge, which all say the same about the lens) is skipped, and at most `MAX_CANDIDATES` are returned. Whether a suggested edge is straight in reality is the operator's call; the misfit check catches a wrong one. `tests/test_lens_calibration.py` runs the whole step on synthetic stages rendered through known lenses with the overlay's own inverse (`tests/_lens_scene.py`), a 720p deck scene with one-pixel seams included, and expects the pair back within 0.01.

**Routes** `POST /api/wizard/lens/snap` (endpoints + the base64 luma band → five points with their marks), `POST /api/wizard/lens/edges` (the scaled luma → candidates with their polyline, five samples, length and strength, plus the edge map as bytes when `with_map` is `true`) and `POST /api/wizard/lens/fit` (lines of active points → k1, k2, `k2_fitted`, per-line RMS / misfit / predicted curve, rating, hint; at most `MAX_LINES` lines of `MAX_POINTS_PER_LINE` points) all answer 400 on malformed bodies like the other wizard routes. They read numbers strictly (`_json_number` / `_json_int` / `_json_point`: no booleans, no strings, counts whole), and the edges route takes only the scale the wizard scales that snapshot by (`edge_map_scale`), so a request cannot buy a larger map than the wizard sends. **In the wizard**, lines live in the session (`_lensLines`) as endpoints plus middle points in the line's frame `(t, off)`, so an endpoint move keeps every middle point's perpendicular offset and a middle point only moves across the line; the fit runs debounced after every release, an edit drops the answer to any fit already sent (`lensFitSeq`), and a failed fit leaves no earlier result standing; a snap answer lands only on a line still as it was sent; a **Low** fit is shown but not applied (`lensFitApplies`), since its pair is whatever the lines cannot pin down; a line spanning less than `LENS_MIN_SPAN_PX` (mirroring `_MIN_LINE_SPAN_PX`) does not count; a tap is judged in CSS pixels; refreshing the snapshot keeps the lines unless the resolution changed. The browser cuts the band with each cell's centre on the pixel position the server models (a canvas puts pixel centres at +0.5 on both sides of the transform), and scales the edge map by block means (`lensScaledLuma`), which is what the tests model and what keeps a one-pixel seam past a scale of three. The sliders under the result are **Fine-tune**. Every solve (Reference Mapping, Corner Pinning, and the one a lens change starts) lands through `applySolvedPose`: the camera into the form, which is what Review shows and Apply saves, the pins with the snapshot size they were taken on, and the lens pair the request undistorted them with (`lensSolvedWith`). A lens change solves again from those pins (`solveFromPinnedCorners`; pins from a snapshot of another size solve nothing), and Review shows the caution "Lens changed – redo Corner Pinning" whenever the current pair is not the one the pose was solved with: a solve that failed, is still running or had no pins leaves it up. `poseSeq` drops the answer to an older solve and to one sent before a corner was dragged or nudged (a solve records copies of the corners it sent, `wizSolveCorners`), and each Reset restores a `snapshotPose()` (camera, pair and pins together). The five-segment coverage meter is the status language's graded meter (`docs/STATUS_LANGUAGE.md`).

## Calibration points (`scene/calibration_points.py`)

Far-field correspondences for a camera that sees only a narrow strip of the stage from far away, where the four corners leave the far field loose by metres. Each point is two laser distances from two grid corners, a height and a pin on the snapshot; the Setup Wizard edits them in Corner Pinning's experimental **Advanced** section (only with `ui.show_experimental_features`; Apply writes them back either way, the saved ones when the section is hidden).

**One joint fit, never a position first.** `solve_with_points` seeds from `solve_camera_dlt`, places each point by `trilaterate` (circles that miss by no more than `_MEET_TOLERANCE` meet at the gap's midpoint; of the two mirror places, `_pick_by_pin` keeps the one the seed camera projects nearer the pin), then a Levenberg-Marquardt fit (`_fit`) adjusts the 7 camera parameters and every point's x, y against the corner pins (`CORNER_SIGMA`, 3 px: a corner mark on a stage floor is seldom pinned closer), the point pins (`PIXEL_SIGMA`, 1 px) and the distances (`DISTANCE_SIGMA`, 4 cm), pins in native snapshot pixels, each residual in its own sigma, the corner check of the plausibility rules and the reported `corner_residual` included; yaw and roll come back in the corner solve's (-180, 180]. A laser fixes a far point's depth and the pin its width, so reducing either to a position first throws away the half it measures well.

**Plausibility** runs while a point's normalised residual passes `FLAG_SIGMA`, or, for a lone point, a corner pin's (it can bend the camera off them while fitting itself; with two or more, the points check each other, and counting the corners would throw good points away whenever a corner pin is a few px off, exactly when the points help most): three or more points drop the one whose removal leaves the lowest remaining cost and fit again; **two that disagree are both left out** (from a narrow strip neither can show the other wrong, and blaming the larger residual picked the good point often enough to end worse than corners alone); a lone point that disagrees with the corners is left out, and so are points no fit can take at all. A fit that passes all of that is still left out the same way (`REASON_FLOOR`) when it moves the floor across the picture (`_floor_holds`: a 9 x 7 grid of probes, those the corners-only camera puts on the floor no farther than `FLOOR_REACH` times the farthest point) to more than `FLOOR_REACH` (2) times as far, or half as near, as the corners-only camera does, or off the floor: the bend a wrong lone pin makes, which the corner check at 3 sigma misses. A fit that leaves the range `solve_camera_dlt` keeps a camera in (`POSE_PITCH_LIMIT_DEG`, `POSE_FOV_RANGE_DEG`) is left out the same way (`REASON_RANGE`). At 3 px of corner noise it never leaves a correct lone point out in simulation. When no point is used the camera is `solve_camera_dlt`'s own, so a left-out point never moves the pose. Statuses are a wire interface of `/api/wizard/solve`: `ok`, `unverified` (the only point in the fit), `flagged` with its `REASON_*` sentence. A flagged point's position is its trilaterated place, drawn on the snapshot through the solved camera. `scripts/calibration_points_simulation.py` reproduces the accuracy table with the shipped solver.

**The route** takes `calibration_points` on `/api/wizard/solve` (read strictly by `_wizard_calibration_points`, the same `problem()` rule as the config, the pin on the snapshot included, the cap, pins in snapshot pixels undistorted with the lens pair like the corners); without the key the answer is exactly the corners-only one. A body naming its page (`solve_page`, `solve_seq`: the page's `WIZ_SOLVE_PAGE` and `poseSeq`) is recorded as that page's newest solve before the rest of the body is read (`_WizardSolveTurns`, one per server, the last 64 pages); an older one arriving late is refused with 409 before any work, and a joint fit asks `stale` before every iteration and answers 409 once the page has asked for a newer one. With it the answer adds `corner_residual` and one `{status, reason, residual, position, seen}` per point, in order. In the page every solve still lands through `applySolvedPose`, which maps each point's answer back by `calibIndices` (on the request body, not enumerable, so never sent); any change to the points bumps `poseSeq` and solves again (deleting a complete point that was not left out, a saved one included, forgets the pose first, `calibForgetPose`, so a solve that fails or is superseded leaves nothing of it; a delete clears a point solve still to come), so an answer for an older point list never lands, and a point made incomplete leaves the pose instead of staying in it. Each point's `position` is the one its answer carried (none for a point left out: its place is its distances', not the solve's), and a pose set any other way (a Reset, a camera field, a solve without the points) takes answers and positions away, so Apply saves a position only with the pose it came from. While any point exists when its answer lands (`calibHold` is read then, so a point added while a solve was out counts), no solve snaps the corner handles to its reprojection (a fit with points is least squares, and a point made incomplete for a moment leaves a corners-only solve): snapped corners would be the next fit's pins. For the same reason a projection never replaces those pins: while the grid is unchanged, `updateAllOverlays` puts the Corner Pinning handles back on the pins the last solve took while points exist (`calibHeldPins`, kept as fractions of the snapshot so another resolution maps, dropped by any other pose change, saved by Apply as `camera.corner_pins` and held again when the next run starts, so a run that only edits a point does not drift the pose; Reset Corners lets go of them for the restored pose's reprojection); nothing solves from a projection by itself (a point without an answer reads Not solved until the operator changes a corner or a point); and Reference Mapping's rigid-shift solve leaves the points out, as does the solve a lens change starts from that solve's pins (`pinnedCorners.withPoints`). Corner taps pick a waiting point's corners only in the full view while the Advanced section is open (adding a point or choosing its corners leaves Fine adjust), a snapshot of another size drops where the last solve saw each point, and a Reset gives back the places its pose's solve gave the points unchanged since. A new point's dot starts at the snapshot's centre and counts only once moved (`pinned`). Apply saves complete points only, so Review lists an incomplete one with its chip. A point's drag moves its drawing in place, because a touch stops reaching the page once the element it began on is removed.

**Config** (`CameraConfig`): `corner_pins` (the four corner pins, DSL, DSR, USR, USL, the Setup Wizard's last solve with the points took, as fractions of the snapshot so another resolution still maps, each coordinate within `CORNER_PIN_REACH` snapshots; empty when it has none; written by Apply beside the pose and the points, anything else dropped with one WARNING; not device-local), `calibration_points` (`list[CalibrationPointConfig]`, at most `MAX_CALIBRATION_POINTS`: two distinct grid corners by name, the two laser distances in `(0, 200]` m, `height` above the corners' level, the pin as a fraction of the snapshot, inside it, and `position`, where the Setup Wizard's solve of the saved pose put the point (empty when none did or it was left out; an output kept with the pose, so it does not follow a later grid edit, and a pose changed outside the Setup Wizard, on the Camera tab or by Ctrl/Cmd+S, keeps it). An entry `problem()` rejects is dropped with one WARNING per distinct set of drops (every load builds the camera again), never clamped, since a clamped distance is a wrong measurement; a value that is no number reads as NaN, which it rejects too, and a missing corner or pin is never filled in (the defaults are a blank corner and a NaN pin). Written only by the Setup Wizard's Apply (`calibSaved`; the Operator Screen's Ctrl/Cmd+S writes the pose alone), listed read-only on the Camera form, carried into the diagnostics bundle by its config dump, and read by nothing at runtime: the solved pose is what the HUD uses)

## Peer authentication (`web/peer_auth.py`)
Peer-to-peer config broadcast is HMAC-signed. The web PIN is the HMAC key; the PIN itself never leaves the host.

- **Signature headers:** `X-Auth-Signature` (hex HMAC-SHA256) + `X-Auth-Timestamp` (unix seconds).
- **Signed payload:** `method\npath\nSHA256(body)\ntimestamp` – path includes the query string when present, so a query is semantically bound to the signed operation.
- **Timestamp window:** `TIMESTAMP_WINDOW_SECONDS = 30` – tolerant of typical NTP-free LAN skew, too narrow for offline replay to be practical.
- **Pre-auth body cap:** `_check_auth` requires `Content-Length` and rejects requests over `peer_auth.MAX_SIGNED_BODY_SIZE` (1 MiB) with 413 before reading – the verifier has to hash the full body before the HMAC proves the sender, so an unauthenticated client could otherwise force an unbounded spool.
- **The PIN never travels:** a third-party script authenticates by cookie (browser flow) or signs with `peer_auth.sign()`.
- **Host binding not included:** OpenFollow only performs broadcast-to-all operations and restricts targets to private IPs (`_is_private_peer_ip`), so cross-peer replay produces only the same effect a legitimate broadcast would have.
- **Offline brute-force note:** a captured signed request lets an attacker test candidate PINs offline. The HMAC construction only hides the PIN from the wire – it does not make a short / low-entropy PIN strong. Operators wanting meaningful resistance should use a longer shared secret; a future KDF derivation would raise the cost further.

## Browser auth (`_check_auth` + `login_submit`)
- `web_pin` non-empty → every non-asset route requires either a valid HMAC signature (peer path above) or the `_openfollow_auth` cookie.
- Cookie is set with `httponly=True`, `path="/"`, **`samesite="strict"`**. Strict blocks the browser from attaching the cookie to any cross-site request, which defeats CSRF without a separate token layer. OpenFollow is LAN-only so the reduced cross-site ergonomics are acceptable.
- `/login`, `/assets/*` and the About pages are exempt from auth. The login page shows no station state.

## Refused names and failed saves (`_check_auth`, `static/js/save-feedback.js`)
- **A change through a name the station does not accept** (an `Origin` / `Referer` host outside `_allowed_request_hosts()`, the CSRF / DNS-rebind defence) is answered by `_refused` in the shape its caller reads: JSON `{error, action, href}` for HTMX and script requests, and a page for a plain form post (`_is_navigation`: `Sec-Fetch-Mode: navigate`, else `Accept: text/html` without `HX-Request`) – the login page with the reason where "Incorrect PIN" sits, or `refused.tpl`. Never Bottle's bare 403 page.
- **The address offered** is the local address the connection arrived on (`SERVER_ADDR`, recorded by `_QuietHandler.get_environ`): the browser just reached it, and no DNS lookup is involved. Loopback (a proxy on the box) offers none.
- **On page load**, every full page (index, wizard, login, about) spreads `_page_host_context()`, so a page opened through such a name shows the red banner before anything is edited. The `Host` header decides it; the refusal stays the backstop, because a reverse proxy can make `Host` and `Origin` disagree.
- **Every save reports failure the same way** (`window.OpenFollow.saveError`): the form's ring flashes red for 0.55 s like the green save flash, and a red line under its actions says what the station observed plus one next step, until the next edit or save. Non-GET HTMX requests are covered globally (`htmx:responseError` / `htmx:sendError`); a script-driven save calls `saveError.show(box, info, lead, near)`. A dialog that closed before its request failed hands the line to the section last clicked. Don't add toasts, alerts or modals for a failed save; the offline update upload keeps the updater's own dialog, and the save to a USB storage device ends its dialog on the export's result (a refused start still reports through `saveError`). `tests/test_save_feedback.py` fails a template or input plugin that saves by script without the helper.

## Login throttle (`web/login_throttle.py`)
Per-IP exponential-backoff lockout on PIN authentication. Without this, a 4-digit PIN is exhausted in seconds over a LAN – no rate limit, no attempt counter, no back-off.

- **Curve:** 1 s after the first failure, doubling each subsequent failure (1, 2, 4, 8, 16, 30 …), capped at `_MAX_LOCKOUT_S = 30 s`. The exponent saturates at 60 to keep `2 ** n` inside float range under sustained probing – without this an attacker could drive `failures` past 1024 over ~8.5 hours and turn brute-force traffic into server 500s via `OverflowError`.
- **Two vectors, one throttle:** `setup_routes` builds a single `LoginThrottle` instance shared by `POST /login` (form path) and the peer-auth signature verifier in `_check_auth`. An attacker can't sidestep the lockout by alternating between vectors. The lockout check runs **before** any HMAC compute on the peer path, so a flood of bogus signatures can't keep the verifier hashing.
- **Reset on success:** a correct PIN check (`record_success`) clears that IP's history. Idle entries (no failure within `_RESET_AFTER_S = 10 min`) get GC'd by both per-IP cleanup in `remaining_lockout` and a periodic full sweep in `record_failure` (amortised O(1) per call) – required because an attacker rotating through one-off IPs would otherwise grow `_entries` without bound.
- **`_is_stale` requires both conditions:** an entry is collectable only when the idle threshold has passed *and* `lockout_until` has expired. Defends against a misconfigured `reset_after_s < max_lockout_s` where the per-IP GC could otherwise drop an entry mid-lockout, letting an attacker reset their failure count by waiting one idle window.
- **Wire response:** locked-out callers get `429 + Retry-After: <seconds>`. The header is computed via `math.ceil(remaining)` so it never overshoots the cap (`int(remaining) + 1` would advertise `31` on a `30 s` cap). `bottle.abort()` discards thread-local response headers, so the 429 is raised as `HTTPResponse(headers={"Retry-After": …})` directly – not via `abort()`.
- **Threading:** every public method takes the instance lock, and `now = self._clock()` is read **inside** the critical section so a contended caller can't compute `lockout_until = now + delay` against a stale timestamp.
- **Per-IP, not per-account:** acceptable because there is only one shared PIN. Legitimate users behind the same NAT share lockout – a known trade-off on a LAN show network. No persistence across server restarts; matches the LAN threat model.
- **Coverage:** 100% line + branch in `tests/test_login_throttle.py` (mock-clock unit tests, including thread-safety stress) + integration tests in `tests/test_web_server.py` (live server, real `urllib`, both vectors). Module is in the `mypy --strict` batch.

## Broadcast target restriction
`_send_config_to_peer` / `_send_config_import_to_peer` refuse to POST to non-private IPs – `ipaddress.IPv4Address.is_private` covers RFC 1918, link-local, and loopback, which is the set a legitimate peer can plausibly have. Closes the SSRF vector where a crafted beacon advertised an attacker-chosen endpoint (e.g. `web_port=22` or an internal service port).

## Service name as an argument
`_is_valid_service_name` rejects any value starting with `-` as well as anything outside its pattern, so `update_service_name` can never be parsed as a `systemctl` option; an invalid name falls back to the default unit (`_service_unit_name`).
