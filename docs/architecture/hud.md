# Operator Screen (HUD)

Covers `video/overlay.py`, `video/hud_render.py`, the GL display (`video/gl_display.py`, `video/gl_cadence.py`), `runtime/overlay_*`, `window.py`, the on-screen menus. The rules that apply everywhere are in [CLAUDE.md](../../CLAUDE.md).

## HUD rendering (decoupled from buffer flow)
The HUD is **not** in the GStreamer chain. This section describes the Cairo Operator Screen; the GL display, which draws video and HUD in one GL area where the platform supports it, keeps the same HUD thread and pacing and is described [below](#the-gl-display). On the Cairo Operator Screen the video sink (`gtksink`) is wrapped in a `Gtk.Overlay`; a `Gtk.DrawingArea` is layered on top via `Gtk.Overlay.add_overlay()` with `set_overlay_pass_through(True)` so it doesn't intercept input.
- The DrawingArea's `draw` signal calls `HudRenderThread.paint` (`video/hud_render.py`), which only pastes the picture on screen. The display refresh paces the drawing (`attach_hud(..., tick=)`): at each tick the `HudRender` thread, when idle, starts a picture of the state current at that tick with `CairoOverlayRenderer.draw(cr, w, h, state)`, at the screen's device scale; the tick a set number of refreshes later puts it on screen and asks GTK for the redraw that shows it. A repaint no tick asked for (a video frame under the HUD, an expose) pastes the same picture, so every position reaches the screen the same whole number of refreshes after it was sampled. A lone picture that misses its tick is shown late and changes nothing, since a busy web request can stall one; 3 misses among the latest ceil(60 / interval) pictures (never fewer than 3), about 60 refreshes at the current interval, lengthen the interval to the least they needed. Once the latest ceil(120 / interval) pictures all finished within 70 % of a shorter interval, the interval drops straight to the least such one, but no lower than one above the interval that last lengthened; a steady window at that floor lifts it. So the long interval a stall leaves recovers in two windows, while a slow picture that recurs every few dozen settles at the interval it fits, or, when it recurs too rarely to sit in every steady window there, at the least interval where it misses alone, instead of alternating between two intervals. Without that hysteresis a drawing time near a refresh boundary alternates between two intervals, and a moving marker hitches on every longer one. With no display there are no ticks and nothing is drawn. An exception in the HUD tick is logged and the tick carries on, since GTK drops a tick callback that raises. Two pictures take turns: a new one starts only at a tick, after the finished one went on screen, so it is drawn into the one shown before. The frame loop shares the GTK main thread with the draw callback, and a paint cannot be interrupted, so the HUD is drawn off it: a marker update or an output never waits for a whole paint. The two threads still share the Python interpreter, so a heavy HUD still costs the frame loop some time.
- The frame loop hands the renderer a new `OverlayState` every frame and never changes or reuses one it handed over: the render thread may still be drawing it. Only the render thread calls `draw` and touches the renderer's caches.
- A `Gtk.Widget.add_tick_callback` runs every display vsync (~60–120 Hz), independent of source buffer rate, so a 0-fps NDI source does not freeze the HUD.
- First-frame / caps detection is a downstream pad probe in the receiver (see [video](video.md#receiver-videoreceiverpy--generic-orchestrator)).
- `CairoOverlayRenderer.measured_fps()` reports how many HUD pictures the render thread draws a second (at most the display refresh rate), **not** source buffer rate. Use `receiver.source_framerate` (parsed from caps) for actual source FPS.
- **Don't re-couple the HUD to buffer flow** (e.g. by reintroducing `cairooverlay` or a videorate-driven redraw).

## GL or Cairo Operator Screen
At startup `AppRuntimeServices._choose_gl_display` picks how the Operator Screen is drawn. The GL display (`video/gl_display.py`) runs when all of these hold; otherwise the Cairo Operator Screen above runs, and the log says which and why:
- `display.operator_screen` is `"auto"` (the default). `"cairo"` keeps Cairo; it is set in `config.toml` only, has no web control and stays on its station (see [config](config.md)). It is for a driver that renders GL wrong without an error, and for a support comparison.
- `gl_display_blocker`: Linux (GTK3's GL area never draws on macOS) and PyOpenGL installed.
- `probe_gl_context`: GDK makes a GL context on the window whose renderer is not a software one (llvmpipe, softpipe, swrast draw on the CPU, slower than Cairo), and the display's shaders compile and link in it.
- `GlDisplay` builds: its sink needs GStreamer's `fakevideosink` (plugins-bad).

If the GL area then fails to start, or 120 renders in a row fail, `GlDisplay.on_unavailable` hands over without a restart (`_fall_back_to_cairo`): the window brings the Cairo HUD layer back, the HUD thread draws canvas-sized pictures again, and the receiver rebuilds its pipeline on the platform sink (`drop_display`).

The GL display takes video frames only between `accept_frames` and `release_frames`. The receiver releases them before every NULL transition, and accepts again in `_prepare_sink`, when the shared sink joins the next pipeline after the old one stopped; so every input plugin and the placeholder build through `prepare_sink`, and nothing the old pipeline still pushes while it stops can reach the screen.

## The GL display
`video/gl_display.py` is the receiver's video sink and the window's main widget in one: a `Gtk.GLArea` the window renders once per display refresh (`attach_gl_display`, `queue_render(frame_clock)`), in place of `gtksink` and the Cairo HUD layer.
- **Video.** The sink is `capsfilter (I420) ! fakevideosink` with handoffs, not `appsink`: `fakevideosink` announces `GstVideoMeta`, so a decoder writes into it without a copy. Each frame goes into a `Cadence` (`video/gl_cadence.py`) with its arrival time and its running time (the segment's running time of its pts, which keeps counting through a looping clip). By default the cadence shows the newest frame at the refresh after it arrives and holds only that one; `~/.openfollow-gl-cadence` = `locked` or `capped`, read when the display is built, picks the even cadence or its capped form, for an A/B only. A render uploads the frame's Y, U and V planes (laid out by the buffer's video meta, else the caps) and converts them in a shader from the caps' matrix and range.
- **Frames held.** The display holds frames only between `accept_frames` and `release_frames` (see [above](#gl-or-cairo-operator-screen)): a decoder must never stop while one of its frames is held.
- **HUD as layers.** The HUD thread draws onto a `LayerContext` (`runtime/overlay_layers.py`) instead of a canvas-sized picture, and hands over `Layers`: a list of sprites, bottom first. A **kept** picture from a cache (`GridCache`, `ZoneCache`, `PathCache`, `ConeCache`, `PanelCache`, the modal scrim) passes by reference through `keep()`; what is drawn between kept pictures is recorded and cut to its ink at each kept picture and each `cut()`. A segment ends only at the top level (no save or group open beyond `mark_top`'s, identity matrix), so no drawing state crosses into the next one. On a plain cairo context, or below the top level, `keep` returns False and the caller pastes the picture; on a plain cairo context `cut` and `mark_top` do nothing, so the Cairo Operator Screen runs the same drawing code into one canvas-sized picture.
- **Textures.** `SpriteTextures` keeps one texture per kept picture, by identity and holding the picture, and deletes it when the picture leaves the list; drawn sprites reuse the last list's textures. A new GL context starts with none.
- **Logs.** Every 10 s the display logs `GL HUD` (pictures shown, the share on time, the refreshes each is held), `GL main thread` (time per render, video upload and sprite upload, count, p50 and p99) and `GL video cadence` (frames shown, how many refreshes each stayed on screen, skipped and late frames, the wait from arrival to screen and the arrival spread). The wait is measured from the refresh's frame-clock time, so a frame that arrives between that time and the render reads slightly negative.

**Do not:**
- draw into a kept picture: a cache whose picture changes makes a new one on a layered canvas (`GridCache` reuses its picture only on a plain cairo context), since the compositor may still show, and has uploaded, the old one;
- end a segment below the top level, or make a drawing's state depend on a save or group across a `cut()`;
- build a pipeline on the shared sink without `prepare_sink`, or hold a frame past `release_frames`.

## HUD layout
- **Top-left:** the help panel (`key_toggle_help`), or its key hint while closed. While any menu screen is open, the menus' one key list instead (`build_help_sections(mode="menus")`), the same on every screen: `CairoOverlayRenderer.draw` draws it after `_draw_menu_screen`, never a screen itself, and no screen names its own keys. The Button Detection Wizard is not a menu here (every pad button is the input it records) and names only `Esc` itself
- **Top-right:** system stats (`draw_system_stats`) and the status badge (`overlay_status_badge.py`, one row per `_status_flags` entry), drawn last so modals sit on top. A supply under voltage or a throttled CPU is one of its error rows, held 10 s after the last active reading (see [diagnostics](diagnostics.md#power-supply-and-throttling-power_healthpy)). So is a control conflict: a single row for all the markers this station controls that a peer also controls, as its catalog-sync beacon advertises. One marker reads `Control conflict: Marker 3 (Lead)` (its catalog name, `Control conflict: Marker 3` without one), several read `Control conflict: Markers 3, 4, 5`, ids ascending and cut with `…` past `CONTROL_CONFLICT_ROW_MAX_CHARS` so the row stays on one line of the badge. The row never names the other station; the web marker table, `/api/stats` and the diagnostics bundle do. Each of those markers' cards takes the error fill, as for a missing controller. `marker_catalog/control_conflicts.find_control_conflicts` decides it at each runtime-stats publish (4 Hz, on the frame loop); the HUD, `/api/stats` (`marker_conflicts`), the web marker table and the diagnostics bundle all read that one result
- **Bottom-left:** the info panel (`IP Address:` + `Video Source:`) and the virtual fader stack
- **Right side:** one marker card per viewer marker, each carrying its controller badge (see [input](input.md#marker-card--controller-binding)); an assist-mode ghost has no card

## Cone markers

`MarkerConfig.marker_style` is `crosshair` or `cone`. `cone` draws a truncated cone between the stage plane and the marker's Z, below the stage included, from `cone_base_diameter` / `cone_top_diameter` (m) and `cone_thickness` (px), filled at `cone_opacity` when `cone_filled` (the side under a left-lit gradient when `cone_shaded`), and ignores the ball / crosshair / Z line / ground circle fields; the silhouette edges come from `scene/solver.cone_silhouette_angles` in closed form and are inserted into the rings (`cone_ring_angles`), with the convex hull `ring_silhouette_indices` only where the camera looks into the cone or part of it is behind the camera; the renderer keeps each cone as a picture (`ConeCache`) and draws it again only when an input it is drawn from changes, and the mouse grab area is the base ring built from half of `cone_base_diameter`.

Trigger zones are kept as one picture too (`runtime/overlay_draw_zones.ZoneCache`); what it is keyed on, how it is sized and why its labels are grayscale are in the [zones guide](zones.md#overlay-rendering-runtimeservices_marker_visualspy).

The cone, path, zone and panel caches each choose their picture's box and draw it through one helper, `overlay_picture.box_picture` (a new picture at the target's device scale, translated to the box's origin, with the target's font options when the drawing has text), and put it on screen through `overlay_picture.paste`: a kept layer on a `LayerContext`, one paint elsewhere.

The main grid and the ground grid are one picture (`overlay_draw_scene.GridCache`), the whole canvas at the screen's device scale, pasted at its origin as the first thing in the scene; the paste covers only the 32-pixel tiles the lines run through, as the rest of the picture is clear. On the GL display it, like every cached picture here, is kept as its own layer instead of pasted (see [The GL display](#the-gl-display)). It is let go while neither grid is drawn or no scene is (a menu screen, the Button Detection Wizard, no camera), and drawn again when either grid's visibility, the grid config, the ground grid's corners or height, the grid colour, opacity or thickness, the camera, the lens, the frame size or the device scale changes. Pasted onto the cleared picture it is pixel for pixel what drawing the grids there gives; a new input either grid is drawn from must be added to its key and to the redraw test's cases in the same change.

The HUD's corner icon, help panel, info panel and system stats are kept as pictures too (`overlay_picture.PanelCache`), each cropped to its ink (`overlay_picture.ink_picture`, shared with the zones) and drawn again only when its key changes: the text it shows, the info panel's error state, the help panel's width, the frame size, the device scale and the font options. On a clear canvas a kept panel is pixel for pixel the panel drawn directly; over a grid line or a marker a pixel can differ by one step in 255, as the panel is blended as a whole. A new input a panel is drawn from must be added to its key and to `tests/test_overlay_picture.py`'s redraw cases in the same change. A crosshair marker sends all its points (ball, crosshair, Z line, ground circle) through one projection.

## Floor height and the ground grid

Every element that stands on the floor under a marker (the Z line, the ground circle, the cone base, the assist ghost's ring) asks `overlay_draw_scene.floor_z_at(state, x, y)` for its height; nothing else reads `grid_config[5]` for a marker's floor. `floor_z_at` returns the ground grid's `z_offset` when it is active and `(x, y)` is inside its polygon (`zones.geometry.point_in_polygon`, even-odd, XY only, whatever the marker's own Z), else the main grid's `z_offset`. The `ConeCache` key carries that height, so a cone redraws when its floor changes.

The ground grid (`GroundGridConfig`, the experimental `ground_grid` feature) is one polygon of up to 64 PSN-absolute `[x, y]` corners at an absolute `z_offset`. With the `ground_grid` feature on and at least three corners, `enabled` makes it active (the floor redirect) and `visible` draws it, each on its own; the feature off hides it at once, since `sync_ground_grid_config` reads the list every tick. `sync_ground_grid_config` copies it into `OverlayState.ground_grid_*` every tick. `draw_ground_grid` runs right after `draw_grid`: the main grid's lines as it draws them (`scene/ground_grid.main_grid_steps`: spread edge to edge, so a gap is the spacing only for a whole multiple of it, and continued past the rectangle; past the 200-line cap an even share of them) clipped to the polygon by `scene/ground_grid.grid_segments_in_polygon` and kept until the polygon, the grid or the height changes, plus the outline, at the ground grid's height and in the main grid's colour, thickness and opacity, through `_draw_world_lines` so the lens bows them. The main grid still draws across the polygon. The mouse grabs a marker by its ring on that same floor (`scene/ground_grid.floor_height`, the config-side twin of `floor_z_at`) and reads the cursor on the floor the marker was grabbed on for the whole drag, so the grab never jumps; the detection pin, the OSC height placeholders and the marker card stay on the main grid.

## Measuring the Operator Screen

`tests/_hud_scenes.py` builds the bench scenes: runs of frames with markers on fixed curves, so marker cards, zone occupancy and the caches change as on a station. `tests/test_hud_cost_proxies.py` counts what a picture costs over them instead of timing it (the grid, path, zone and cone pictures drawn again only when an input changes, through `tests/_hud_cost.count_calls`), so a cost regression fails on any machine. `scripts/hw_validation/hud_bench.py` times the same scenes on a canvas-sized picture, as the Cairo Operator Screen draws them, and compares two checkouts; see its [README section](../../scripts/hw_validation/README.md#operator-screen-drawing-cost). On a station the GL display's own logs (see [The GL display](#the-gl-display)) say whether the HUD keeps its refresh and how frames meet it; `/api/stats` gives the frame loop and HUD rates for either Operator Screen, and what the Operator Screen costs (below).

## What the Operator Screen costs (`/api/stats` → `hud`)

`HudRenderThread` feeds `video/hud_metrics.HudMetrics` where the work happens, on either Operator Screen: the render thread reports each picture's CPU time for clearing and drawing (`time.thread_time`); the Cairo Operator Screen's GTK draw each repaint's (the paste, `paint`), the GL display each render's (`GlDisplay._render` → `gl_rendered`); the display tick each refresh and whether it showed a new picture; and a buffer probe on the shared display sink (`gtksink`, or the GL display's sink bin) each video frame (`GstNativeSinkReceiver.set_display_frame_listener`). `/api/stats` publishes the last closed window of about two seconds as `hud`, `null` until the first window closes and for a window with no display refresh (a station without a display, or with its display gone). A cost nothing reported in the window is `null`, never 0, so the Cairo-only and the GL-only fields tell which Operator Screen ran:

| Field | Meaning |
|---|---|
| `window_s` | How long the window ran, in seconds |
| `picture_ms`, `clear_ms`, `draw_ms` | CPU per picture on the render thread: clearing (or allocating) plus drawing. A layered picture for the GL display starts empty, so `clear_ms` is `null` there and `draw_ms` includes cutting it into layers |
| `paint_ms`, `repaints_per_s` | Cairo Operator Screen: CPU per repaint on the GTK main thread (the paste) and how many repaints a second; every video frame repaints the HUD too |
| `gl_render_ms`, `gl_renders_per_s` | GL display: CPU per render on the GTK main thread (video and HUD uploads, compositing) and how many renders a second, one per refresh. CPU only: time the thread waits on the driver is in the `GL main thread` log's wall time |
| `pictures_per_s`, `refreshes_per_s` | New pictures shown and display ticks a second |
| `interval_refreshes` | The pacing interval when the window closed: refreshes each picture is held |
| `picture_refreshes` | How many refreshes each picture stayed on screen, as counts (`{"2": 59, "3": 1}`); everything at `interval_refreshes` is an even HUD |
| `video_frames_per_s`, `video_refreshes`, `video_replaced` | Frames reaching the display sink (the No Signal placeholder's included), how many refreshes each stayed on screen (2 for 30 fps on 60 Hz), and frames replaced before a refresh showed them. Counted as each frame showing at the refresh after it arrives, as `gtksink` and the GL display's default cadence show it; under a `locked` or `capped` cadence the `GL video cadence` log is the measure |
| `render_thread_id` | The render thread's native id, to read its CPU time from `/proc` (Python 3.13 gives threads no OS name) |

GTK can run the tick a little faster than the display refreshes, so a refresh count is approximate by one now and then. `scripts/hw_validation/hud_probe.py` reads these with the CPU per thread on a running station; see its [README section](../../scripts/hw_validation/README.md#operator-screen-on-a-running-station).
