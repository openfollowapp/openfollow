# Config model

Covers `configuration.py`, `config_restore.py`, `restore_hold.py`, config import / export / reset / restore, hot reload and live-apply. The rules that apply everywhere are in [CLAUDE.md](../../CLAUDE.md).

All config lives in `config.toml` (auto-reloaded when file changes on disk).

## Sub-config notes

- **`MarkerConfig.control_frame`** (`stage` / `heading` / `camera` / `screen`) and **`control_heading`** (degrees, wrapped into one turn, the camera-yaw convention) pick the stage directions *relative* input (keyboard, gamepad, 3D mouse) steers in; see [input](input.md#control-frame-inputcontrol_framepy). A file, API body or peer carrying `invert_control_direction` is read through `apply_renamed_marker_keys`: `true` as `heading` / `180`, `false` as `stage`, unless it also carries `control_frame`.
- **`MarkerConfig.marker_style = "cone"`**: see [hud](hud.md#cone-markers).
- **`CameraConfig.calibration_mode`** (`simple` / `advanced`) and **`calibration_marks`** (`list[CalibrationMarkConfig]`, at most `MAX_CALIBRATION_MARKS`, 12): the Setup Wizard's last calibration. A mark has `id` (1-999, unique), `name` (at most 60 characters, `P<id>` when blank), `kind` (`known` / `triangulated`), `x` / `y` / `z` (m; a triangulated mark reads only `z`), `from_a` / `from_b` (the ids a triangulated mark is measured from) with `distance_a` / `distance_b` in `(0, 200]` m, `pin` (`[x, y]` as fractions of the snapshot, inside it; empty when not pinned, which a triangulated mark may not be) and `position` (where the solve of the saved pose put a triangulated mark; empty when none did). A value the kind does not read is stored as 0. An entry `problem()` rejects, a repeated id, a From that is not kept or loops back (`calibration_mark_drops`), and in Simple anything but the four known corners (ids 1-4: DSL, DSR, USR, USL) is dropped with one WARNING per distinct set, never clamped, since a clamped distance is a wrong measurement. **Simple's corners are the grid's**: `reconcile_simple_corners`, run in `AppConfig.__post_init__`, after every `apply_section_data` and on a Camera & Grid template load, moves a corner the grid has moved and drops its pin, so a write that brings pins for a new grid applies the grid first (the Setup Wizard's Apply, an import). Not device-local: the marks travel with the camera on export, import and push. They describe the pose they were solved for, so a camera write that changes the pose or FOV without bringing marks clears the marks, the mode and the height (`apply_section_data`); the Camera form only shows the camera, and the Setup Wizard, Apply to all stations, an import of a current export and a Camera & Grid template write a pose with its marks. See [web](web.md#camera-calibration-from-marks-scenecalibration_pointspy).
- **`CameraConfig.calibration_height`** (m, `None` when not entered): the camera's exact height the Setup Wizard's solve held, stored with the calibration and listed read-only beside it on the Camera form. A value that is no finite number (a boolean included) or lies beyond `MARK_REACH_M` is dropped to `None` with one WARNING, never clamped; a section write takes a JSON number or null, and anything else keeps the saved height. `None` is left out of the TOML. It travels with the camera like the marks; Restore defaults clears it.
- **`CameraConfig.calibration_lens_rating`**, **`calibration_time`**, **`calibration_source`**: what describes the Setup Wizard's last calibration, shown in the Camera form's Calibration column. The rating is one of `CALIBRATION_LENS_RATINGS` (`excellent` / `good` / `fair` / `poor` from the Lens step's fit, never Not usable since such a fit is not applied, `user_input`, `loaded`, `opencv` for a lens converted from an OpenCV calibration file), else `""`. The time is ISO 8601 with its UTC offset, to the second, by the clock of the browser that saved it; one without an offset or unreadable is `""`. The source is display text, `redact_uris_in_text` and `CONTROL_CHARS_RE` applied and cut to `CALIBRATION_SOURCE_MAX_LEN` (200). Anything of the wrong type is `""`. They travel with the marks: a camera write that brings marks clears each one it does not bring as text, a pose or FOV change without marks clears all three with the rest of the calibration, and a lens change without a rating clears the rating (`apply_section_data`). The source is stripped of control characters before it is redacted, so none can split a credential's key. An unquoted TOML datetime with an offset reads as its text. The station stamps the source itself (`_shown_source_text`: the input's display name and its credential-free live label) on a camera write to `/api/config/camera` that brings a time and no source and is not a push, which is what the Setup Wizard's Save and finish sends.
- **`CameraConfig.lens_k1` / `lens_k2` / `lens_cx` / `lens_cy`**: the lens, defined in `lens_model.py`'s docstring; the centre in half-diagonals from the frame centre (x right, y down), so the four fit any resolution of the same picture shape. `__post_init__` clamps each centre axis to `±C_BOUND` (a value that is no number reads as 0) and pulls a lens that cannot follow the picture out to its corners back along the pair's ray, never moving the centre, with one WARNING. Not device-local and not device identity: the lens travels with export, import and push, and Restore defaults resets all four. `effective_lens(cfg)` is the lens everything draws and maps with; the Camera group reads the stored fields only to show them, and the Setup Wizard to edit them. See [web](web.md#lens-distortion-from-straight-lines-scenelens_fitpy-sceneedge_snappy-sceneedge_chainspy-lens_modelpy).
- **Saved lens calibrations are not config.** `web/lens_calibrations.py` keeps one JSON file per calibration in a `lens-calibrations` directory beside `config.toml` (`calibrations_dir`), so export, import and push never carry them. Each holds `name` (1-60 characters, no control characters, unique ignoring case), `k1`, `k2`, `cx`, `cy` (the lens as the config holds it, all four required: real numbers, never a boolean, the centre within `C_BOUND` per axis, and `lens_warp_is_valid` on the four), `saved` (ISO date), `width` / `height` (the snapshot's pixel size, `1..MAX_SIDE`, or `null` when saved before any snapshot) and `openfollow_version` (the `__version__` that wrote it). A file whose size is missing or invalid still lists, with no size. The file name is a slug of the name plus a digest of it ignoring case, never a client path; a save writes atomically and replaces the file of the same name ignoring case. A file that does not read or fails a check is left out of the list with one WARNING, never deleted. The on-station settings backup (`privilege/settings_backup.py`) holds the directory.
- **`DetectionConfig`**: see [detection](detection.md#config).
- **`PathsConfig`**: show_paths, slide_time (s, 0-10, default 1), paths (`list[PathConfig]`: name, active, closed, release_at_start, release_at_end, points `list[PathPointConfig]` of x / y / z / radius). See [paths](paths.md).
- **`GroundGridConfig`**: enabled (drop markers inside it onto its height), visible (draw it), z_offset (absolute world Z), vertices (up to 64 finite `[x, y]`, PSN-absolute); both flags need the `ground_grid` feature and three corners. See [hud](hud.md#floor-height-and-the-ground-grid).
- **`UiConfig.shown_features`**: the General tab's Features list, the keys of `FEATURE_KEYS` that are on, stored in that order; unknown, duplicate and non-string entries drop, anything but a list reads as `DEFAULT_SHOWN_FEATURES` (every key not in `EXPERIMENTAL_FEATURES`). **Config-only** features (`CONFIG_ONLY_FEATURES`: `paths`) gate like any other but are not offered: the Features table, the `features` section and its `FIELD_RULES` cover `OFFERED_FEATURES` only, so no web route turns one on or off, and only `shown_features` in `config.toml` (or an import or push carrying it) does. A config with `show_experimental_features` and no `shown_features` loads as every offered feature on when it was true, the default otherwise (`migrate_ui_keys`, also run on an import or push from an older station); the old key is never written. It travels with export, import and push, and is saved by the Station Settings Save (`/section/general` applies the `features` section, one bool per key); it is never section-broadcast. **A feature is gated where its subsystem reads its config, never by writing the config:** `feature_on(cfg, key)` for a plain check, `feature_gated(section, cfg, key)` for a section with its own `enabled` switch (detection, RTTrPM, zones, touch remote), `services.midi_patches()` for MIDI and `PsnReceiver.set_enabled` for PSN input. Turning one off keeps every setting it gates.
- **`OscConfig.allowed_sender_ips`** normalises to `list[str]` in `__post_init__`, so malformed TOML can't reach the filter; see [input](input.md#osc-input-allowlist). **`OscConfig.listen_iface`**: see [network](network.md#osc-listener-multicast-membership).

## Validation contract (REQUIRED for every config change)

All config values must survive a hand-edited `config.toml` and a crafted POST to `/section/<name>` without crashing the app or silently producing bad behavior. Python dataclasses **do not** validate field types at runtime – a `fov = "wide"` entry in TOML would flow straight into `project_points` and crash rendering; a `transparency = 5` would mis-render forever.

When you add, remove, or change a field on any config dataclass:

1. **Normalise in `__post_init__`.** Use the helpers at the top of [`configuration.py`](../../openfollow/configuration.py): `_coerce_float` / `_coerce_int` / `_coerce_hex_color` / `_coerce_choice`. They coerce to the target type, clamp to `[lo, hi]` if supplied, and fall back to the declared default when coercion fails.
2. **Re-run `__post_init__` after web-form saves.** `apply_section_data` in [`web/routes.py`](../../openfollow/web/routes.py) dispatches on section name and invokes the re-run for every dataclass that has one (currently: `camera`, `grid`, `ground_grid`, `marker`/`movement`, `controller` (+ `gamepad`/`keyboard`/`mouse`), `osc`, `detection`, `otp_output`, `rttrpm_output`, `trigger_zones`, `paths`). Extend the dispatch when adding a new section with its own `__post_init__` – otherwise a crafted POST bypasses validation that a hand-edited TOML would trip.
3. **Add regression tests in `tests/test_configuration.py`.** Cover: wrong type (string / `None`), out-of-range, enum mismatch, and (for list fields) heterogeneous entries. Follow the existing `test_grid_config_*` / `test_detection_config_*` pattern – one `@pytest.mark.parametrize` per failure mode.
4. **Register every web-form field in [`openfollow/web/validation.py`](../../openfollow/web/validation.py)::`FIELD_RULES`.** Each entry MUST use the same parser as `_SECTION_FIELD_PARSERS` (or the corresponding inline parser used by the special sections in `apply_section_data`), the same `lo` / `hi` / `choices` / `pattern` bounds enforced by `__post_init__`, and a `human_error` string the user will see on blur. Templates render every input with the standard markup (see [`partials/grid.tpl`](../../openfollow/web/templates/partials/grid.tpl)): `hx-get="/api/validate/<section>/<name>"`, `hx-trigger="blur changed delay:200ms"`, `hx-target` pointing at a sibling `<span class="field-error">`, `hx-include="closest form"`, and `aria-describedby` / `aria-invalid` for accessibility. The form-gate JS in `base.tpl` (`refreshFormGate`) only disables actual config-save/broadcast submit controls – Save buttons MUST be `<button type="submit" class="save-btn">…</button>` and Broadcast buttons MUST carry the inline `broadcastSection(...)` call shape (`<button class="broadcast-btn" onclick="broadcastSection(…)">…</button>`); the gate selector matches `button[type="submit"].save-btn, button.broadcast-btn[onclick*="broadcastSection"]`. Buttons that share the `.save-btn` / `.broadcast-btn` *styling* but trigger non-save actions (Export Configuration, the keyboard map's Reset to Defaults) MUST NOT carry `type="submit"` or `broadcastSection(...)` – that's what keeps them clickable while a validation error is visible.

   Every string-typed `FieldRule` declares its sanitisation contract: `strip_whitespace` (defaults to `True`), `max_len`, optional `sanitiser` (defaults to control-char + bidi-override stripping), `pattern` for syntax checks. The contract MUST match what `__post_init__` actually does to that field on Save – a `__post_init__` strip / coercion that lacks a matching `FieldRule` flag is a CI failure. Lists with per-entry rules (`allowed_sender_ips`, `colors`, `controlled_marker_ids`) get a `custom` validator that surfaces the offending entry: `"Entry 3 ('999.0.0.1') is not a valid IPv4 address."`.

   Cross-field auto-corrections (`marker.max_speed >= min_speed`, `detection.inference_size` snap-to-32, `psn_system_name` empty fallback) are surfaced via `note()` as advisory **blue** notes – not errors. They DO NOT set `aria-invalid` and DO NOT gate Save; the server-side `__post_init__` chain repairs the value at save time.

   The consistency test in [`tests/test_template_validation_consistency.py`](../../tests/test_template_validation_consistency.py) walks every partial and asserts this wiring. A new field that ships without a `FIELD_RULES` entry, or an `<input>` whose `name` matches an entry but lacks the standard markup, fails CI. **Code review should reject any web form change that does not extend the registry.** [`wizard.tpl`](../../openfollow/web/templates/wizard.tpl) is not a partial, so the test does not cover it.

A config change that skips any of these four steps is incomplete, regardless of what the happy path looks like. Code review should reject it.

## Hot-reload rules (`apply_runtime_config_changes`)
- **Requires app restart:** `web_port` and `web_bind_iface` stay restart-required (the listening socket can't move under a request being served on it; server-restart-in-place is fragile, and both are rare changes). `display.operator_screen` is read once at startup; it is set in `config.toml` only and has no web control (see [hud](hud.md#gl-or-cairo-operator-screen)). The on-screen Network screen's `Serve web UI on all interfaces` clears the pin and requests the restart itself - it is the documented lockout escape and is deliberately not gated on a writable network backend. `controller.keyboard_layout` / `keyboard_variant` take effect only when the kiosk session starts Cage, so a save never restarts by itself: Keyboard Input offers Restart OpenFollow while they, or the system file's model or options, differ from the session's (see [input](input.md#keyboard-layout-keyboard_layoutpy-packaged-session))
- **Next start:** `network.backend` and the update / time-sync group (`update_github_repo`, `update_include_prereleases`, `auto_update_check`, `auto_time_sync`, `time_sync_server`) are read once at startup and the reload never applies them (it only mirrors `network` into `app._config`, the adapter stays), so a saved change, by hand or by an import, takes effect at the next start without asking for one. The installer and the online-sync worker read them off `app._config`, and the manual update check reads the same running values through `update_source_provider`, never the file.
- **Features:** `ui.shown_features` applies live. The ui block records the old list and each gated block also runs when its key flipped (`_flipped`): `psn_input` (`apply_psn_input_change`), `rttrpm`, `zones`, `detection` (through the usual detection paths, with the gated config), `midi`, and the paths engine; the rest are read live each frame or request.
- **Live update (no restart):** **video_source_type and any plugin config field** (auto-detected via `plugin.config_changed()`; the receiver live-swaps the active input plugin in place via `swap_video` → `receiver.swap_input`, transactional with rollback – see [`AppRuntimeServices.swap_video`](../../openfollow/services.py)), camera, grid, ground_grid, movement (speed limits + default position), marker, controller, **mouse3d** (read thread runs for the handler's lifetime; the block swaps the mapping config and the `enabled` gate is read live in `InputManager.update`), osc, trigger_zones, paths, controlled_marker_ids, viewer_marker_ids, parked_marker_ids, psn_system_name, **psn_source_iface, otp_output, rttrpm_output**, **detection**: on→on (worker drains a staged config between frames; rebuilds the inference session in-thread when model / storage_path changes), on→off (the worker is signalled; an inference in flight finishes off the frame loop), and switching on, an `inference_size` change or an edit with no running detector (`swap_detector` builds the detector off the frame loop and rebuilds the pipeline around it on the main loop; see [detection](detection.md#pipeline-integration)), **window_width / window_height, web_pin**
- Restart triggered via `_web_commands.request_restart()`, polled in `_check_restart_request()`, which acts on it no sooner than `RESTART_GRACE_S` (0.5 s) after the latest request, so the request that asked for it gets its answer out first
- Saving config with restart-requiring changes triggers an automatic restart via the hot-reload file watcher within ~1 animation frame
- **A runtime save never writes `app._config` whole onto an existing file.** The reload leaves some fields alone (the restart-only ones, `marker_move_speeds`) and has not seen an edit made since its last poll, so a whole-config write undoes those edits. Every save of the running config goes through `save_config_fields` (on screen via `app_modes._persist_config(app, *names)`), which writes only the named fields (one dot addresses a sub-config field) onto the file as it is on disk, under `config_write_lock` and from one strict read of it (`missing_ok=False`, so neither an empty file nor one renamed away mid-save reads as every default), and leaves the mtime alone so the reload still applies everything else the file holds. The exceptions: a missing file is written whole, and an empty or unreadable one, which otherwise fails the save, is replaced whole only under `replace_unreadable` (the lockout escape). The reload makes the same read: it skips an empty file and retries one that does not parse on every poll, each warning once per mtime, and retries a missing one. A source picked on the Operator Screen (NDI, Pi Camera, USB camera) is saved the same way: the receiver hands the pick to `on_source_picked`, and `app_modes.save_source_pick` puts it into `app._config` before it saves that field alone, so the reload finds nothing to reconnect. The GTK main loop takes that lock, so a web route must never hold it across slow work. The reload mirrors the fields of every video input that is not running, so an on-screen switch to one is built from the file's values. An auto-chained URL editor or value picker holds the picked type itself (`source_type`) and puts it into `app._config` only once it runs, so a reload in between has nothing to undo. A plain edit holds none: once a reload has brought up another input, its confirm saves the field alone, without a swap
- **An empty or unreadable `config.toml` is never read as the defaults, nor written over.** A file holding only whitespace is treated like one that does not parse, everywhere. *Reads whole* has one definition, `_read_whole`: the bytes build an `AppConfig`. Valid TOML of the wrong shape (`grid = 5`) does not, so it counts as unreadable for the file, its backup, the startup restore and every save, and the non-strict `load_config` recovers from any failure rather than raising.
  - *Reads that only show the config.* `load_config` recovers from `config.toml.bak` (a backup that does not read whole counts as none), else takes the defaults, and logs that once per state of the file. Every read in the web UI that only shows the config (pages, `_check_auth`, the login, and through `_last_whole_config` the render-only routes and the diagnostics bundle) goes through `ParsedConfigCache`, which serves a file that does not read whole as it last read whole: the `.bak` is a save behind and could hold an older PIN, or none. `setup_routes` warms it from the file the station just started on, and an entry is kept only if no newer one was stored while it was parsed. Only when the file was already broken at start does a page fall back to the `.bak` or the defaults, whose blank `web_pin` asks for no login.
  - *Reads that write or hand on.* Every web route that writes the config, Broadcast All, Export and a template capture read it with `load_config_for_save`, which raises `ConfigFileUnreadableError` (an `OSError`; `ConfigFileEmptyError` for a blank file); a missing file is read as the web UI last read it whole (`_config_for_save`), so a write or an Import after a deletion keeps the PIN and identity the page showed; elsewhere it reads as `load_config` reads it, the backup else a first run. `services._record_path` takes the running config when the file does not read whole, and a scan in the tests pins every remaining non-strict read. `save_config_fields` and `save_config_change` read it the same way, a missing file writing the running config whole. A refusal comes before anything is archived, so a refused import, reset or push leaves no settings archive.
  - *The write.* `save_config` reads the file once, refuses one that is empty or does not read unless `replace_unreadable`, and snapshots the bytes it checked to `.bak`; replacing an unreadable file takes no snapshot, so the last good `.bak` stays.
  - *What may replace one.* An empty file holds nothing to keep: at startup `restore_empty_config` (also run by the macOS launcher before it seeds) copies a readable backup over it byte for byte and leaves the `.bak`, or removes it so the start is a first run exactly like a missing file. The restore takes the `.bak`, which is a save behind: a PIN set in the last save before the file was emptied is not in it. The running station never restores: an empty file it finds is most often an editor between its truncation and its write, which a restore would race; the reload skips it. An unreadable file may hold hand edits: startup runs on the backup (else the defaults) and writes nothing; only an Import from a file (`_import_base`, not a push) or a backup restore replaces it, keeping the device identity of the last whole read (else the backup's), archiving the file it replaces under the name and catalog of that last whole read, and the on-screen lockout escape.
  - *What the operator is told.* A web write answers 409 `{error, action}` through the route plugin `_refuse_over_unreadable_config`, which the save-feedback line shows; a peer's refusal reaches the sending station as that peer's `reason` in `peer_results`. The on-screen saves that report a failure (source and URL edits, value pickers, the source pick) show their unsaved banner; the zone-overlay toggle, path recording and the move-speed flush only log. Both say what is wrong and one step, from `config_problem_words`, and never name a file: an empty file is restored by restarting OpenFollow, or started again with default settings when no backup reads whole; an unreadable one is replaced by importing a settings file or restoring a backup. The 409 also carries `settings_file` (`empty-restorable`, `empty`, `unreadable`), from which a sending station words a peer's refusal in the third person. The diagnostics bundle's config section has a *Config file health* row (`config_file_health`) that names the state of the file and its backup and none of their contents

## Live-apply pattern
Service rebind/restart live-apply paths (sockets, worker threads) route through `_apply_with_fallback("name", apply_fn, on_failure=…)` in [`configuration.py`](../../openfollow/configuration.py). The helper logs duration on success, logs `logger.exception` plus runs `on_failure` on exception, and returns so the dispatcher keeps applying subsequent settings – a single failed live-apply on one service must not bypass live-applying everything else. Pure in-memory mutations that can't fail at runtime (e.g. `window_width/height` resizing the GTK window, `web_pin` mirroring into `app._config`) skip the helper because there's no failure mode to revert from.

Each underlying service exposes a small `restart(...)` (or `rebind(...)` for receivers) that does `stop()` → reassign attributes → `start()`. Marker registrations and other shared state survive across the cycle by living on instance attributes that aren't touched by `stop()`/`start()`. `start()` mints a **fresh stop event per generation** and hands it to the threads it spawns – never `clear()` a shared one, or a send thread that outlived `stop()`'s join is put back to work alongside the new generation. Every loop, send, and socket-retry path judges its own generation's event, so a dying survivor can't tear down the live socket. See [`OtpServer.restart`](../../openfollow/otp/server.py), [`RttrpmServer.restart`](../../openfollow/rttrpm/server.py), and [`PsnReceiver.rebind`](../../openfollow/psn/receiver.py).

The four-state transition matrix (off→on, on→on with new cfg, on→off, off→off) lives on `AppRuntimeServices.apply_*_change` orchestrators in [`services.py`](../../openfollow/services.py); the dispatcher only knows to call them with the new cfg.

For services with a worker thread (e.g. detection), the GTK thread does NOT mutate worker state directly. Instead the GTK side calls `service.reload_config(new_cfg)`, which stages the config under a small lock; the worker drains the staged value at the top of its next loop iteration. Heavy operations – backend session rebuilds for [`PersonDetector`](../../openfollow/video/detection.py) on a model / storage_path change – happen on the worker thread, not the GTK thread. Failure during a worker-side rebuild keeps the prior config + backend so the loop never lands in a half-applied state. The pattern is "single-element pending slot, latest-wins" – no queue, no event drain loop.

## Config transfer (export / import / restore defaults / restore a backup)
- **Export:** `GET /api/config/export` returns the full config as a downloadable JSON file. Device-local fields are stripped from the payload by `_config_dict_redacted`: `web_pin` (login secret), `detection.storage_path` (an absolute path that only makes sense on the exporting host), the interface pins that name this box's NICs (`otp_output.source_iface`, `rttrpm_output.source_iface`, `osc.listen_iface`, each OSC destination's `source_iface`), `interface_labels`, which name its adapters, and `controller.keyboard_layout` / `keyboard_variant`, which describe the keyboard plugged into it. `touch_remote.enabled` (whether this station takes remote driving) is stripped too; the touch remote's tuning travels. So is `display.operator_screen`, set for this station's GPU and driver, and `marker_move_speeds`, this station's per-marker speeds, which are runtime-authoritative: an import keeps the live speeds. Stream credentials (`rtsp_user` / `rtsp_password` / `srt_passphrase`) deliberately **stay**: a station PIN is that station's own login, while a camera password is shared by every station pointed at the same camera, so stripping it would break the fleet-provisioning workflow export and broadcast exist for. They are redacted in the diagnostics bundle instead, which is the artefact operators attach to public issue reports.
- **Import:** `POST /api/config/import` applies imported JSON, then writes the device-identity snapshot back (captured before the section apply, restored after, in `_apply_import_data`). Section-level peer broadcast / `/api/config/<section>` go through `strip_device_local_fields`, which drops the same per-section set (`_DEVICE_LOCAL_FIELDS_BY_SECTION`), and so does every section the import applies. `interface_assignment` is dropped whole (`_DEVICE_LOCAL_SECTIONS`): its per-destination keys are not known in advance. OSC destinations are rebuilt wholesale from the file, so their pins are carried over by destination id; a destination new to this station starts blank. A storage path from another machine must never land here – it would be unwritable and break model storage / export. A file import (not a push, `_apply_import_data(pushed=False)`) also restores what describes this station's own setup and has no section form the import could go through (`_apply_file_import_data`): the marker selection (normalised by `marker_id_list`, as a load does, a controlled marker always viewed), the detection masks and `masks_enabled`, the fields of every video input rather than only the running one's, the 3D Mouse and operator-messages sections, MIDI patches, virtual faders, the gamepad mapping (`button_raw_indices`, `swap_triggers`, `mapped_controller_*`) and its `button_name_style`, `ui.developer_mode`, `paths.show_paths`, and the settings read at startup, `network.backend` and the update / time-sync group (`update_include_prereleases`, `auto_update_check`, `auto_time_sync`, `time_sync_server`), each normalised by its sub-config's `__post_init__` (`AppConfig.normalise_startup_settings` for the last four); a push leaves all of them as they are. The startup ones land in the file and take effect at the next start (see Hot-reload rules). An export → Restore defaults → import round trip therefore restores every exported setting. Before it saves, the import archives the settings it replaces (see [Settings backup](update.md#settings-backup)), whoever sent it: this page or another station's Broadcast All.
- **Pushed settings** ([`web/pushed_settings.py`](../../openfollow/web/pushed_settings.py)): Broadcast All and a section Broadcast mark their request `?from=<station name>` (`_push_path`, signed with the rest of the path under a PIN); an unmarked write (the Setup Wizard's Finish, a script) is no push. **A push never carries `psn_system_name`** (`_PUSH_EXCLUDED_FIELDS`): both senders drop it, which is what protects a receiver on an older release, and a marked receive drops it again. A file import still applies it, so a replacement unit restored from its predecessor's export comes back under that name. A marked import or section write backs up as `-push-` (a section only once it is known to apply, both before the write lock) and lands in `ConfigWebServer.pushed_settings`, in memory, the newest ten listed and older ones counted by id. The address recorded is `_client_address()`, the connection's `REMOTE_ADDR`, never `request.remote_addr`, which Bottle takes from a client-set `X-Forwarded-For`. `base.tpl` polls `/api/pushed-settings` every 3 s on every station page and shows the list in the shared modal, locked, waiting while another modal is open and stepping aside while a device-password prompt is up, which it would otherwise make inert; **Remove Warning** posts the newest id it showed to `/api/pushed-settings/remove`, so a push that arrived since stays, with the `run` it read the list from: ids start at 1 on every run, so a removal from before a restart is refused (409). The page then reloads, because its forms still hold the values from before the push, and a removal made elsewhere reloads every page loaded before a push of this run (`received`, the run's count, against the page's first answer), once no other modal is open. A hidden tab skips the poll and asks again when shown. The modal is redrawn whenever its list changes, not only on a newer push. The Operator Screen shows the newest push as an info row (`runtime/pushed_settings_hud.py`, posted from housekeeping) and, while one was pending when the Settings menu opened, lists **Remove Pushed Settings Warning** first in that menu; the menu's rows are fixed while it is open, so an arriving push cannot move the highlight onto another action, the highlight starts on the row below it, and the entry removes only up to the push it was opened with. Stations on 0.5.0-rc1 and earlier send no name: their Broadcast All reaches the import as `?skip_restart=1`, which `_pushed_by` takes as a push from an unnamed station (listed by its address, the name kept), and their section Broadcast carries no marker and raises nothing.
- **Restore defaults:** `POST /api/config/reset` writes `reset_config_to_defaults(current)` – a fresh `AppConfig()` carrying the same device-identity snapshot – through `save_config` and requests the restart. While an update is queued or running it answers 409 and changes nothing; otherwise the backup is taken first, then the write and the restart request run as one step under the update lock (`WebCommandQueue.restart_after`), so an update cannot land between them. **The restart is part of the operation.** A section save only writes fields `apply_runtime_config_changes` applies, so it finishes live; a whole-config reset also touches fields it does not – `network.backend` is startup-only by design, the update / time-sync group is read off `app._config` and never reassigned, and `marker_move_speeds` is deliberately runtime-authoritative. Left running, the station keeps acting on their pre-reset values and the next move-speed change writes every old speed back over the reset, so it would silently, partially undo itself. `psn_system_name` follows the preserved `station_id` via `derive_station_name`, the way a first run seeds it: resetting it to the bare `"OpenFollow"` default would let the next restart's `_bootstrap_station_identity` silently rename the station. The marker catalog (`markers.toml`), the media gallery and the model store are separate files and are untouched. Like an import, the reset archives the settings it replaces first.
- **Restore a backup** ([`config_restore.py`](../../openfollow/config_restore.py)): `GET /api/config/backups` lists the station's own settings archives (see [Settings backup](update.md#settings-backup)), both folders merged, newest first by the time in the name: `name`, `kind` (`update`, or the web backup's kind), `before` (the row's label), `version` (the manifest's `version` for a web backup, `from` for an update backup, else the name's `-v<version>`; shown as `packaging` spells it), `created` (the manifest's, else the name's, ISO 8601 UTC) and `newer`. Never a path or anything an archive holds but its manifest. A folder that is missing lists as none; one that is there but does not list answers 500, so the page never shows a station without the backups it has. `POST /api/config/backups/restore` takes `{"name"}`: a body without a string name is 400; a name the listing does not hold is 404 (the request text never becomes a path); a busy update is 409, as for Restore defaults; a backup whose version is newer than `openfollow.__version__` is 409 with both versions (a Debian `~rc` reads as the pre-release, an epoch and a revision such as `-1` are dropped; a version that does not parse, or a running 0.0.0, is never newer). The archive is read whole before anything is written, as a stream never extracted: a gzip tar under `MAX_ARCHIVE_BYTES` that unpacks to at most `MAX_UNPACKED_BYTES` (pax and long-name headers count), each member checked from its header (no absolute or `..` name, regular files and folders only, each under `MAX_MEMBER_BYTES`, together under `MAX_TOTAL_BYTES` and `MAX_MEMBERS`, no file where another needs a folder), only `config.toml`, `markers.toml`, `templates/user/…` and `lens-calibrations/…` kept, the catalog parsed as TOML and `config.toml` loaded strict through `load_config` from a scratch file, so every field goes through `__post_init__` as a hand-edited file does; any failure is 422 and writes nothing. Then the settings it replaces are archived (`restore`; a failed backup does not block it), the catalog and folders are staged beside their targets (with the folder each target is moved aside to, so everything that takes space is made before anything is held), and under the update lock (`restart_after`) the config is saved, the staged copies are renamed into place and the restart is requested. **One restore at a time:** the route holds a lock from its recovery to its commit (another restore's recovery would remove this one's staged copies), and a restore while one runs, or while one's restart is pending, answers 409 "Another restore is running." / "Restore again once the station is back." **Nothing lands over a restore before its restart** ([`restore_hold.py`](../../openfollow/restore_hold.py)): every writer of a restored part writes inside `unless_held` (`save_config`, `save_catalog`, `write_user_template` / `delete_user_template`, `save_calibration`), and the restore takes `restore_hold.GATE` across its config save, `hold(config, catalog, templates/user, lens-calibrations)` and its renames, so a write lands before the restore or not at all. A held write raises `HeldForRestartError`: a web write answers 409 "OpenFollow is restarting." / "Save again once it is back." through `_refuse_over_unreadable_config` (the catalog routes take their in-memory change back first), an on-screen save says "OpenFollow is restarting after a restore.", and a peer's catalog change stays in memory with an INFO line. **Once the config is in place, the station always restarts.** Everything that takes space is staged first, every file and folder synced: the commit journal `.restore-commit.pending` beside the config (naming the catalog for the recovery), the catalog beside its target, each folder with the empty folder its target is moved aside to, and, under the config lock, the restored `config.toml` itself (`stage_config`, the same checks and `.bak` snapshot as `save_config`). The commit (`StagedRestore.commit`) only renames: the journal to `.restore-commit`, then the config. Either failing raises with nothing changed, nothing held and no restart. From the config on, every restored part is held and nothing escapes the commit: each part is renamed in turn (each parent synced), a part that cannot move in keeps the station's own (a folder moved aside is put back; if that fails too, the next start, finding no journal, puts it back), cleanup failures are swallowed, an unexpected error names every part not reached, and the journal is removed when the commit ends. So `restart_after` always requests the restart, and the route answers 500 naming what was not written, with `restarting` and `instance`; the page keeps its restart progress, shows the reason in it and confirms with a caution toast after the reload (saying too when no backup was made). `recover_interrupted_restore(config_path)` runs at app start before the config is read, and, under the lock, before every restore: with the journal on the disk the restore had committed and is finished from its staged copies, config included; without it they are discarded and a folder left moved aside (not an empty placeholder) is put back; the journals and every other leftover are removed. A member name that is no text or holds a NUL is a damaged archive. Background savers that meet the hold (the move-speed flush, the touch remote's detection switch-off, a paths change, a peer's catalog change or delete) log it at INFO as the restart. The config keeps this station's `_DEVICE_IDENTITY_FIELDS` and `psn_system_name` (`restored_from_backup`), and `enforce_network_mode` runs again for the kept mode, so a Simple station never takes a pin back; in Advanced the backup's own plane pins return. The catalog is written to this station's `markers_catalog_path`, never the archive's. A part the archive does not hold is left as it is. Like an import from a file, a restore replaces a `config.toml` that does not read, keeping the identity of its last whole read; an empty one is refused for the restart that restores it.
- **The device-identity set is one list, `_DEVICE_IDENTITY_FIELDS`**, shared by import, restore-defaults and a backup restore via `capture_device_identity` / `restore_device_identity` (one dot addresses a sub-config). It holds what identifies or connects *this box* rather than describes the show: `psn_source_iface`, `web_pin`, `web_port`, `web_bind`, `web_bind_iface`, `station_fqdn`, `network_mode`, `station_id`, `markers_catalog_path`, `testpattern_selected_media`, `detection.storage_path`, `display.operator_screen`. A default or foreign value in any of them locks the operator out of the only interface an offline show LAN has, moves the station off its interface, makes two stations claim one name, re-mints its identity, points a path at a directory that does not exist here, or brings back a GL display this station's driver was set to avoid. `otp_output.source_iface`, `rttrpm_output.source_iface`, `osc.listen_iface`, `video_input_iface` and the OSC destination pins are deliberately **not** in the set: blank means "follow `psn_source_iface`", which is preserved, so resetting them drops nothing off the network. `web_bind_iface` is the opposite case: blank means every interface, so a reset would unpin the web UI.
- Import saves in one request and every section applies live through the hot-reload path, so it never asks for a restart. Stations on 0.5.0-rc1 and earlier push Broadcast All to `?skip_restart=1`, which marks it as a push (see Pushed settings above).
- Routes are registered before the wildcard `/api/config/<section>` routes to avoid interception
