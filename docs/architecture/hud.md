# Operator Screen (HUD)

Covers `video/overlay.py`, `runtime/overlay_*`, `window.py`, the on-screen menus. The rules that apply everywhere are in [CLAUDE.md](../../CLAUDE.md).

## HUD rendering (decoupled from buffer flow)
The HUD is **not** in the GStreamer chain. The video sink (`gtksink`) is wrapped in a `Gtk.Overlay`; a `Gtk.DrawingArea` is layered on top via `Gtk.Overlay.add_overlay()` with `set_overlay_pass_through(True)` so it doesn't intercept input.
- The DrawingArea's `draw` signal calls `HudRenderThread.paint` (`video/hud_render.py`), which only pastes the picture on screen. The display refresh paces the drawing (`attach_hud(..., tick=)`): at each tick the `HudRender` thread, when idle, starts a picture of the state current at that tick with `CairoOverlayRenderer.draw(cr, w, h, state)`, at the screen's device scale; the tick a set number of refreshes later puts it on screen and asks GTK for the redraw that shows it. A repaint no tick asked for (a video frame under the HUD, an expose) pastes the same picture, so every position reaches the screen the same whole number of refreshes after it was sampled. A lone picture that misses its tick is shown late and changes nothing, since a busy web request can stall one; 3 misses among the latest ceil(60 / interval) pictures (never fewer than 3), about 60 refreshes at the current interval, lengthen the interval to the least they needed. Once the latest ceil(120 / interval) pictures all finished within 70 % of a shorter interval, the interval drops straight to the least such one, but no lower than one above the interval that last lengthened; a steady window at that floor lifts it. So the long interval a stall leaves recovers in two windows, while a slow picture that recurs every few dozen settles at the interval it fits, or, when it recurs too rarely to sit in every steady window there, at the least interval where it misses alone, instead of alternating between two intervals. Without that hysteresis a drawing time near a refresh boundary alternates between two intervals, and a moving marker hitches on every longer one. With no display there are no ticks and nothing is drawn. An exception in the HUD tick is logged and the tick carries on, since GTK drops a tick callback that raises. Two pictures take turns: a new one starts only at a tick, after the finished one went on screen, so it is drawn into the one shown before. The frame loop shares the GTK main thread with the draw callback, and a paint cannot be interrupted, so the HUD is drawn off it: a marker update or an output never waits for a whole paint. The two threads still share the Python interpreter, so a heavy HUD still costs the frame loop some time.
- The frame loop hands the renderer a new `OverlayState` every frame and never changes or reuses one it handed over: the render thread may still be drawing it. Only the render thread calls `draw` and touches the renderer's caches.
- A `Gtk.Widget.add_tick_callback` runs every display vsync (~60–120 Hz), independent of source buffer rate, so a 0-fps NDI source does not freeze the HUD.
- First-frame / caps detection is a downstream pad probe in the receiver (see [video](video.md#receiver-videoreceiverpy--generic-orchestrator)).
- `CairoOverlayRenderer.measured_fps()` reports how many HUD pictures the render thread draws a second (at most the display refresh rate), **not** source buffer rate. Use `receiver.source_framerate` (parsed from caps) for actual source FPS.
- **Don't re-couple the HUD to buffer flow** (e.g. by reintroducing `cairooverlay` or a videorate-driven redraw).

## HUD layout
- **Top-left:** the help panel (`key_toggle_help`), or its key hint while closed. While any menu screen is open, the menus' one key list instead (`build_help_sections(mode="menus")`), the same on every screen: `CairoOverlayRenderer.draw` draws it after `_draw_menu_screen`, never a screen itself, and no screen names its own keys. The Button Detection Wizard is not a menu here (every pad button is the input it records) and names only `Esc` itself
- **Top-right:** system stats (`draw_system_stats`) and the status badge (`overlay_status_badge.py`, one row per `_status_flags` entry), drawn last so modals sit on top. A supply under voltage or a throttled CPU is one of its error rows, held 10 s after the last active reading (see [diagnostics](diagnostics.md#power-supply-and-throttling-power_healthpy))
- **Bottom-left:** the info panel (`IP Address:` + `Video Source:`) and the virtual fader stack
- **Right side:** one marker card per viewer marker, each carrying its controller badge (see [input](input.md#marker-card--controller-binding)); an assist-mode ghost has no card

## Cone markers

`MarkerConfig.marker_style` is `crosshair` or `cone`. `cone` draws a truncated cone between the stage plane and the marker's Z, below the stage included, from `cone_base_diameter` / `cone_top_diameter` (m) and `cone_thickness` (px), filled at `cone_opacity` when `cone_filled` (the side under a left-lit gradient when `cone_shaded`), and ignores the ball / crosshair / Z line / ground circle fields; the silhouette edges come from `scene/solver.cone_silhouette_angles` in closed form and are inserted into the rings (`cone_ring_angles`), with the convex hull `ring_silhouette_indices` only where the camera looks into the cone or part of it is behind the camera; the renderer keeps each cone as a picture (`ConeCache`) and draws it again only when an input it is drawn from changes, and the mouse grab area is the base ring built from half of `cone_base_diameter`.

Trigger zones are kept as one picture too (`runtime/overlay_draw_zones.ZoneCache`); what it is keyed on, how it is sized and why its labels are grayscale are in the [zones guide](zones.md#overlay-rendering-runtimeservices_marker_visualspy).

The main grid and the ground grid are one picture (`overlay_draw_scene.GridCache`), the whole canvas at the screen's device scale, pasted at its origin as the first thing in the scene; the paste covers only the 32-pixel tiles the lines run through, as the rest of the picture is clear. It is let go while neither grid is drawn or no scene is (a menu screen, the Button Detection Wizard, no camera), and drawn again when either grid's visibility, the grid config, the ground grid's corners or height, the grid colour, opacity or thickness, the camera, the lens, the frame size or the device scale changes. Pasted onto the cleared picture it is pixel for pixel what drawing the grids there gives; a new input either grid is drawn from must be added to its key and to the redraw test's cases in the same change.

The HUD's corner icon, help panel, info panel and system stats are kept as pictures too (`overlay_picture.PanelCache`), each cropped to its ink (`overlay_picture.ink_picture`, shared with the zones) and drawn again only when its key changes: the text it shows, the info panel's error state, the help panel's width, the frame size, the device scale and the font options. On a clear canvas a kept panel is pixel for pixel the panel drawn directly; over a grid line or a marker a pixel can differ by one step in 255, as the panel is blended as a whole. A new input a panel is drawn from must be added to its key and to `tests/test_overlay_picture.py`'s redraw cases in the same change. A crosshair marker sends all its points (ball, crosshair, Z line, ground circle) through one projection.

## Floor height and the ground grid

Every element that stands on the floor under a marker (the Z line, the ground circle, the cone base, the assist ghost's ring) asks `overlay_draw_scene.floor_z_at(state, x, y)` for its height; nothing else reads `grid_config[5]` for a marker's floor. `floor_z_at` returns the ground grid's `z_offset` when it is active and `(x, y)` is inside its polygon (`zones.geometry.point_in_polygon`, even-odd, XY only, whatever the marker's own Z), else the main grid's `z_offset`. The `ConeCache` key carries that height, so a cone redraws when its floor changes.

The ground grid (`GroundGridConfig`, the experimental `ground_grid` feature) is one polygon of up to 64 PSN-absolute `[x, y]` corners at an absolute `z_offset`. With the `ground_grid` feature on and at least three corners, `enabled` makes it active (the floor redirect) and `visible` draws it, each on its own; the feature off hides it at once, since `sync_ground_grid_config` reads the list every tick. `sync_ground_grid_config` copies it into `OverlayState.ground_grid_*` every tick. `draw_ground_grid` runs right after `draw_grid`: the main grid's lines as it draws them (`scene/ground_grid.main_grid_steps`: spread edge to edge, so a gap is the spacing only for a whole multiple of it, and continued past the rectangle; past the 200-line cap an even share of them) clipped to the polygon by `scene/ground_grid.grid_segments_in_polygon` and kept until the polygon, the grid or the height changes, plus the outline, at the ground grid's height and in the main grid's colour, thickness and opacity, through `_draw_world_lines` so the lens bows them. The main grid still draws across the polygon. The mouse grabs a marker by its ring on that same floor (`scene/ground_grid.floor_height`, the config-side twin of `floor_z_at`) and reads the cursor on the floor the marker was grabbed on for the whole drag, so the grab never jumps; the detection pin, the OSC height placeholders and the marker card stay on the main grid.

## Measuring the Operator Screen

`tests/_hud_scenes.py` builds the bench scenes: runs of frames with markers on fixed curves, so marker cards, zone occupancy and the caches change as on a station. `tests/test_hud_cost_proxies.py` counts what a picture costs over them instead of timing it (the grid, path, zone and cone pictures drawn again only when an input changes, through `tests/_hud_cost.count_calls`), so a cost regression fails on any machine. `scripts/hw_validation/hud_bench.py` times the same scenes and compares two checkouts; see its [README section](../../scripts/hw_validation/README.md#operator-screen-drawing-cost).
